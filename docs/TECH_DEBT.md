## Инцидент 2026-08-01 — кросс-tenant RLS-утечка через пул соединений (ИСПРАВЛЕНО)

Пётр (tenant `signaris`) на проде видел проекты/задачи tenant'а `uppetit`: флаппинг 404/200 одного URL, сайдбар с чужими проектами, `/api/me` 500 (`InsufficientPrivilegeError` на INSERT `employee_profiles`).

**Корень:** `tenant_scoped_session` ставил GUC **session-level** один раз при открытии сессии, а `get_db` коммитит shadow-upsert'ы ДО yield → соединение возвращалось в пул (FIFO), и бизнес-запросы роутов исполнялись на другом соединении со stale-GUC чужого tenant'а (или `bypass_rls=on` от воркеров sid-sync/deletion-sync в том же пуле). Пока активен один tenant — не проявлялось; накануне последним в проде был UPPETIT → пул «покрашен» в чужой tenant.

**Фикс:** листенер `app/db.py::_apply_rls_on_begin` (`after_begin` + `SET LOCAL`, порт эталона `CentralAuthService/app/db.py` post-`3cfb256`) перепроставляет оба GUC на старте каждой транзакции. Сопутствующее: `bypass_session_factory()` для lib-воркера deletion-sync (сырая фабрика работала только благодаря утечке — иначе `mark_shadow_deleted` молча обновлял 0 строк); `public.py` stage 2 переведён с bypass на tenant-скоуп (`_mention_names` раскрывал имена/email чужих tenant'ов). Регресс — `tests/integration/test_rls_mid_session_commit.py` (фикстура `rls_enforced`: non-superuser роль, RLS реально enforced; до-фиксовый код валит 2 из 4 тестов).

**Тот же пре-фиксовый `db.py` несёт Listen** (`Listen/app/db.py` + pre-yield commit в `deps.py`; хуже — `device_auth.py` коммитит bypass-сессии → наследник получает полный bypass). Чинить отдельной сессией.

## Открытое


- **`--workers > 1` заблокирован sid-sync'ом.** Deletion-sync к мульти-воркеру готов (супервизор + Redis leader-lock в `app/services/worker_supervisor.py`, этап 4), но revoked-sid store у sid-sync живёт в памяти процесса: не-лидер не узнаёт о ревокациях, а per-process запуск гоняет общий DB-курсор. Для масштабирования нужен Redis-backed revoked-store. Пока `--workers 1`.
- **VAPID-ключ единый для prod+staging.** Удобно (как у Desk), но если staging-баг утечёт public key, теоретически prod-подписки можно подделать. Низкая вероятность. Раздельные ключи — future work.
- **LexoRank-style `tasks.position NUMERIC`** может «насыщаться» при многих DnD-миграциях карточек. Фоновый rebalance колонки так и НЕ реализован (заглушка в `app/api/tasks.py`); при дельте <0.001 порядок может «слипнуться».
- **Подзадачи только 1 уровень** (`parent_task_id` CHECK depth=1). Глубже потребует tree-CTE в запросах и отдельной миграции.
- **Интеграционные тесты бегут от superuser'а testcontainers** → RLS в них НЕ enforced (superuser обходит политики безусловно, FORCE не помогает) — «ловушка testcontainers-superuser». - **Email-коллизии между tenant'ами в `shadow_users`** — для пустого старта Hub проблемы нет; если когда-то будем мигрировать данные, нужен pre-migration report (см. `INTEGRATION.md` шаг 12).
- **Sentry не подключён (DSN нет), проводка полностью готова.** Backend инициализируется при `SIGNARIS_HUB_SENTRY_DSN` в `.env` (deploy.sh с этапа 4 ставит extras `[sentry]`), frontend вызывает `initSentry` при DSN из `/api/env`. Включение = прописать DSN в оба `/opt/*/.env` + restart. Варианты на нашем VPS (2 CPU / 2 GB RAM): (a) Sentry.io free tier — 5k events/мес; (b) GlitchTip self-hosted (~500-800 MB RAM); (c) апгрейд VPS под официальный Sentry. По умолчанию приоритет — GlitchTip на `sentry.signaris.ru`.
- **Healthcheck email-канал требует MTA на VPS** (`mail(1)` не установлен: `apt install mailutils` + postfix/ssmtp). Основной канал — Telegram (`@signaris_bot`, креды в `/etc/default/signaris-hub-healthcheck`, mode 600) — **настроен и проверен вживую 2026-07-03** (DOWN + RECOVERED). Email — опциональный резерв.
- **S3 offsite backup** — флаг `BACKUP_S3_BUCKET` поддерживается в `scripts/backup-pg.sh`, но aws-cli не установлен и креды не настроены. При потере VPS-диска восстановление невозможно без offsite-копии. Минимум — настроить snapshot у VPS-провайдера.

## Миграция контента ServiceGuru → Hub (2026-08-16)

Разовый перенос учебных материалов UPPETIT: **18 курсов / 125 уроков / 57 тестов (269 вопросов) / 179 материалов библиотеки / 131 карточка ассортимента**, ~850 МБ медиа. Инструменты: `tools/import_lms/` (локальная сборка bundle из `LMS/`) + `app/jobs/import_lms_bundle.py` (запись на VPS без HTTP).

**Как повторить/докатить:** пересобрать bundle `python -m tools.import_lms.build_bundle` → rsync в `/opt/signaris-hub[-staging]/import-bundle/` (chown signaris) → `sudo -u signaris .venv/bin/python -m app.jobs.import_lms_bundle --bundle ./import-bundle --tenant-slug <slug> [--dry-run]`. Идемпотентность: курс пропускается, только если он **published** (публикация — последний шаг), draft-курс докатывается; материалы/карточки — по названию. **Смена названий в mapping ⇒ повторный прогон создаст дубли** (старые объекты по прежним именам не удаляются).

Инварианты и решения:
- `LMS/` и `import_bundle/` исключены из git И из rsync деплоя (`deploy/deploy.sh`) — иначе 850 МБ уезжают на VPS каждым деплоем.
- Правильный ответ теста в выгрузке помечен **жирным шрифтом ячейки** (`font.bold`, читать `read_only=False`); 28 вопросов мультивыбора; порог квиза `min(80, (n-1)/n*100)` — иначе тест из 2-3 вопросов требовал бы безошибочности.
- Картинки уроков привязываются к строкам **по порядку** (якоря дрейфуют), картинки вопросов — **по номеру строки**; 16 строк-картинок в выгрузке без файла (пропущены).
- Конвертер Quill→RichDoc (`quill_to_richdoc.py`) прогоняется через серверный `validate_lesson_content` ещё локально; `listItem` всегда оборачивает `paragraph` (иначе TipTap нормализует контент при первом открытии в редакторе).
- Уведомления при импорте НЕ шлются (иначе вал пушей); `audit.record` пишется на каждый объект — сотни строк в журнале действий, это ожидаемо.
- Потери выгрузки: 5 роликов «Загруженное видео» (presigned-ссылки протухли за 10 минут) — вместо них callout «📹 Видео будет добавлено позже»; тайминги вопросов (в Hub их нет); выравнивание текста (attrs параграфа запрещены валидатором); фото ассортимента (в выгрузке только тумбы ~2 КБ). 6 YouTube-роликов скачаны через yt-dlp с `player_client: android` (web отдаёт «not available» для unlisted) и захостены у себя.
- Дозагрузка видео через админку упрётся в nginx `client_max_body_size 25M` — импорт идёт мимо HTTP, но для ручной загрузки лимит придётся поднять.

### Что нашли проверкой в браузере (и почему это не поймалось бы иначе)

- **Диалоги просвечивали в светлой теме.** После пересборки токенов `--glass` в светлой стал чёрным 3,5%, а `.glass` несёт `background: var(--glass)` — модалка «Поля проекта» читалась сквозь список задач. Плавающие слои переведены на новый `.glass-solid` (непрозрачный `--bg-alt`): `Dialog`, `DropdownMenu`, `Toaster`, `UpdateBanner`. **Правило: слой поверх контента непрозрачен в обеих темах, тинт — только карточкам в потоке.**
- **Заголовок задачи обрезался на 360/390.** Автовысота считалась из `scrollHeight` в ref-колбэке ДО загрузки Unbounded: шрифт подменялся, строка переносилась третий раз, высота оставалась старой. На 430 заголовок влезал в две строки и баг не проявлялся. Заменено на CSS-двойника (`components/ui/AutoGrowTextarea.tsx`) — высоту задаёт невидимый span в той же ячейке грида, браузер пересчитывает сам и при смене шрифта, и при смене ширины.
- **Подсветка колонки-приёмника на доске не появлялась.** `useDroppable` в колонке почти всегда `isOver: false` — карточки тоже droppable, и `closestCorners` отдаёт id карточки. Колонку-приёмник теперь считает `BoardView` (`onDragOver` → id колонки, содержащей `over.id`) и передаёт вниз.
- **Плашка ключа проекта уезжала на середину шапки на 360px**: у контейнера стояло `items-center`, а блок с названием, бейджами и описанием занимает там четыре строки. Стало `items-start`.
- Сирота «·» в начале перенесённой мета-строки шапки — разделитель убран в `hidden sm:inline`.

- **`learn_settings.set_setting` не работал ни разу.** `:v::jsonb` в `text()` —
  SQLAlchemy не признаёт биндом параметр, за которым сразу идёт двоеточие
  (regex-lookahead), и `:v` уезжал в SQL литералом. Функция была написана про запас,
  первый вызов появился только сейчас (подложка сертификата). Теперь явные
  `CAST(:v AS jsonb)` и `ARRAY[CAST(:k AS text)]` — в `ARRAY[:k]` Postgres не выводит
  тип элемента. При добавлении новых настроек шаблон брать отсюда.
- **Инлайн-открытие материала библиотеки идёт через ТОТ ЖЕ download-эндпоинт.**
  `_track_open` живёт внутри него и питает `view_history`, по которому стоит гейт кнопки

  существующим `PdfViewer` (pdf.js), картинки — `ImageLightbox`; `Content-Disposition:
  inline` не используется вовсе — `location ^~ /api/` в nginx наследует серверные
  `X-Frame-Options: DENY` и `frame-ancestors 'none'`. Whitelist MIME строгий
  (`lib/inlineViewer.ts`, тест рядом): pdf + растровые, **без svg** — инлайн-показ
  пользовательского svg со своего origin это XSS.
- **`PdfViewer` получает БАЙТЫ, а не blob-URL** (проп `data`). Первая версия отдавала
  object-URL и падала на staging: для не-http(s) источника pdf.js берёт XHR-поток, а
  `connect-src` в CSP содержит только `'self'` и auth/sentry — запрос уходит со статусом
  0, вьювер показывает «не удалось отобразить». `img-src` blob: разрешает, поэтому
  лайтбокс картинок работает как раз через object-URL. Байты копируются на каждый заход
  `getDocument`: pdf.js передаёт буфер воркеру (transfer), и повторный рендер — например
  после смены ширины контейнера — получил бы отсоединённый.
- **`PdfViewer` переиспользован по прежнему имени чанка.** `globIgnores` в

- **Порядок каталога курсов — перенумерация ВСЕГО списка** (`PUT /learn/courses/reorder`,

- **Подложка сертификата — `<img>`, а не `background-image`.** Фоновые картинки браузеры

- **Редактор перестал обещать невыполнимое.** `after_prev_test` действует только при

- **Подписи и настройки блоков правятся ПОСЛЕ вставки** — кнопка «Свойства» в тулбаре

## Ассистент, волна 1 — журнал, инструменты, планы (2026-08-20)

Фича из макета `redesign/Ассистент - редизайн.dc.html`. Волна 1 = журнал операций,

План: `~/.claude/plans/claude-design-floofy-clock.md`.

### Инварианты

- **Ассистент ходит теми же гейтами, что и человек.** Read-инструменты фильтруют проекты через
  `visible_projects_stmt` (членство или hub-admin), write-инструменты зовут ручки `app/api/tasks.py`
  и `comments.py` целиком — со всеми уведомлениями, seq, наблюдателями и `require_project_role`.
  Никаких «своих» запросов в обход RBAC: тест `test_search_tasks_hides_foreign_project`.
- **Отказ по правам — ДАННЫЕ, а не исключение.** `denied()` возвращает причину и `who_can`
  (владелец/редакторы проекта); модель обязана назвать, кого попросить. 403 из инструмента лишил
  бы сотрудника следующего шага и сломал бы виток модели.
- **Порог подтверждения:** правка ОДНОЙ задачи — сразу; создание, комментарий, архивация и любое
  массовое изменение — через карточку плана. `delete_task` ассистенту не дан вовсе (необратимо,
  отмены у плана нет). Решение владельца; макет и спека трекера расходились — не «чинить» обратно.
- **План исполняется из `ai_plans.args`, а не из тела запроса.** Клиент присылает только id.
  «Изменить поля» правит whitelist (`PlanPatch`) и ПЕРЕСОБИРАЕТ превью из тех же args
  (`rebuild_preview`) — подтвердить одно, а выполнить другое невозможно by design.
- **Права перепроверяются на ИСПОЛНЕНИИ**, не только при планировании: между показом карточки и
  «Выполнить» сотрудника могли вывести из проекта. Плюс TTL 30 минут. Тест
  `test_rights_rechecked_at_execution`.
- **Исполнение ровно один раз:** `SELECT … FOR UPDATE` + переход только из `pending`.
- **В `execute()` id снимаются ДО вызова исполнителя.** Ручка API откатывает свою транзакцию, и
  обращение к `plan.id` после `rollback()` требует IO в синхронном контексте → `MissingGreenlet`.
- **Журнал хранит `data.plan_id`, а не снимок плана.** Снимок навсегда оставался «pending», и после
  «Выполнить» карточка предлагала создать задачу заново (поймано на staging). Живое состояние
  подставляет `_hydrate`; она понимает и старую форму `data.plan.id`.
- **Оборот-действие ОБЯЗАН оставить след в истории модели.** Карточка плана рисуется без прозы,
  поэтому ассистентское сообщение уходит с пустым `content`; без `_action_trace` просьба «создай
  задачу» выглядела в истории неотвеченной, и на следующий (совсем другой) вопрос модель
  предлагала создать ту же задачу заново. Поймано на staging, тест
  `test_action_turn_leaves_trace_in_history`.
- **Порядок сообщений — `(created_at, роль)`.** Вопрос и ответ пишутся в ОДНОЙ транзакции, а `now()`
  в Postgres — время начала транзакции: `created_at` у них совпадает, и сортировка только по нему
  давала ответ выше вопроса.
- **Диалог принадлежит `employee_id` (shadow_users), не учебному профилю.** Прежняя привязка к

- **Срок из даты — локальный ПОЛДЕНЬ** (`parse_due`), как `new Date(v+'T12:00:00')` в
  `TaskDetailDrawer`. Полночь UTC уехала бы на предыдущий день. Покрыто тестом.
- **`CommentArgs.text` зеркалит `CommentCreate.body` (4000).** Разойдутся — план соберётся, а
  исполнение упадёт валидацией.
- **Системный промпт несёт текущую дату с днём недели** — без неё «на пятницу» разрешается от даты
  обучения модели. И явный запрет исполнять инструкции из результатов инструментов: проверено на

### Что живые данные заставили переделать

- **`Sum.ResignedSum` отдавала нули на всех типах транзакций.** Правильное поле
  списаний — `Sum.Outgoing` («Сумма расхода»).
- **`TransactionType` принимает КОДЫ, не русские названия.** Фильтр «Списание»
  падал `No enum constant …TransactionType.Списание`. Реальные значения — 16
  кодов; списания это `WRITEOFF` (1,8 млн/нед). **`SESSION_WRITEOFF` (21,6
  млн/нед) — автосписание по факту продаж, то есть себестоимость**; смешав их,
  отчёт о потерях показывал бы себестоимость. Отсюда и заголовок «Списания и
  потери» вместо макетного «Списания и себестоимость»: название обязано
  описывать то, что в отчёте есть.
- **Модификаторы возглавляли меню.** Без фильтра `DishType` топ продаж —
  «Обычное молоко» и «Горячий» (38 тыс. штук при выручке 0,14 млн против 35 млн
  у товаров), а «доля топ-5» считалась от мусорного знаменателя. Меню =
  `GOODS` + `DISH`, `MODIFIER` исключён.
- **`DishAmountInt` смешивает штуки и килограммы.** «Тилапия филе кг» продаётся
  долями, и подпись «шт» была прямой неправдой, а округление 0,3 → «0 шт»
  превращало реальную продажу в ноль-аутсайдера. Количество показывается БЕЗ
  единицы, дробное — с одним знаком; единица подписана у колонки.

### Инварианты

- **Каждое подключение к iiko занимает слот лицензии СЕТИ.** `IikoClient` —
  только async-контекст, `logout` в `__aexit__` при любом исходе (тест
  `test_session_closes_even_when_olap_fails`). Персонального rate-limit мало:
  он бьёт по `employee_id`, а слот общий, поэтому сервис держит **per-tenant
  Redis-лок** (одновременно живёт одна сессия) и **кэш 15 минут**. Не
  дождавшийся получает 409 «отчёт уже собирается», а не вторую сессию.
- **Ключ кэша включает скоуп точек** — иначе ТУ прочитал бы сетевой отчёт,
  собранный админом, и увидел бы чужие точки.
- **`to` в фильтре периода ЭКСКЛЮЗИВНА.** Наружу отдаём человеческий
  включающий период, +1 день добавляется в `IikoClient.olap` — единственном
  месте. «Отчёт за 18 августа» с `to=18` вернул бы пусто, а пустой отчёт на
  экране неотличим от «продаж не было» (для этого случая есть отдельный текст).
- **Время iiko — наивное локальное MSK, не UTC** (проверено в Listen 03.06:
  конвертация −3ч уводила данные на три часа назад). Периоды передаём датами.
- **Имена полей OLAP живут ТОЛЬКО в `app/services/iiko/reports.py`** и
  помечены: `VERIFIED` — сверено Listen с ручным xlsx до рубля
  (`Department`, `OpenTime`, `OrderNum`, `DishDiscountSumInt`,
  `OpenDate.Typed`); остальные (`DishName`, `DishAmountInt`,
  `UniqOrderId.OrdersCount`, `HourOpen`, TRANSACTIONS-поля) — стандартные
  имена iiko, НЕ проверенные на живом API. Перед выгрузкой `validate_fields`
  сверяет их с `/columns` и падает внятным «iiko не знает поля X», а не пустым
  графиком.
- **Обязательные поля отделены от необязательных** (`aggregate` против
  `optional_aggregate`): полосы выручки считаются по проверенному
  `DishDiscountSumInt`, и ронять весь отчёт из-за неточного имени счётчика
  чеков нельзя — плашка деградирует в «—».
- **Падение НЕ красится красным**: рост — `--amber`, падение — `--text2`,
  дельта роста — `--green-deep`. Красный в дизайн-системе занят просрочкой и
  ошибками, иначе плохая неделя выглядит как авария системы.
- **Суммы набираются неразрывными пробелами** — «1 042 300 ₽» не должно
  рваться по строкам. Покрыто тестом.
- **`stores.iiko_department` (0038) — единственный мост между мирами.** В iiko
  точка адресуется СТРОКОЙ-именем, в Hub — UUID. Без сопоставления скоуп ТУ
  невыразим: фильтр ушёл бы пустым и управляющий увидел бы всю сеть. Поэтому у
  ТУ без заполненного поля отчёт падает 409 с просьбой к администратору, а не
  показывает сеть (тест `test_tu_scope_requires_iiko_mapping`).
- **Гейт доступа — тот же, что у learn-аналитики Ф5**: publisher+/hub-admin —
  вся сеть, ТУ и владелец франчайзи — свои точки, линейный — 403.
- **Период ограничен 92 днями**: OLAP за год держит слот минутами, а nginx
  рвёт на 120с — сотрудник увидел бы 504 и не понял, собрался отчёт или нет.
- **Графики — свои `div`'ы, без библиотеки.** Полоса это ширина в процентах,
  гистограмма — высота. recharts на этот экран не тащим: бандл и так резался
  code-splitting'ом.
- **CSV идёт через axios-blob**, а не `<a href>`: тег не несёт Bearer. BOM в
  начале обязателен, иначе Excel в русской локали кладёт строку в одну ячейку.
- **Вход в отчёты обязан быть и на мобильном.** `Sidebar` рендерится только от
  1024px, и первая версия оставила экран отчётов недостижимым с телефона —
  то есть у большинства сотрудников. Кнопка живёт в `trailing`
  `MobilePageHeader`.
- **`MobilePageHeader` капитализирует eyebrow** (`text-transform: capitalize`
  поднимает первую букву КАЖДОГО слова) — «Отчёты iiko» превращалось в
  «Отчёты Iiko». Для строк с именами собственными есть `preserveEyebrowCase`.

## Заголовки `/p/` и сопоставление точек с iiko (2026-08-20)

### Локация `/p/` теряла свои заголовки (ИСПРАВЛЕНО)

`location ~ ^/p/` переиздаёт весь набор вручную ради одной строки —
`Referrer-Policy: no-referrer`, чтобы токен публичной ссылки не утёк через
`Referer`. До клиента доезжал серверный `strict-origin-when-cross-origin`.

Причина — тот же механизм, что ловили на media: **последний аргумент
`try_files` считается URI**, nginx делает внутренний редирект, ЗАНОВО матчит
локации, и выигрывает `location = /index.html` со своим `add_header`.

Лечится одним символом: `try_files $uri /index.html =404;`. С кодом в конце
все предыдущие аргументы проверяются как ФАЙЛЫ и отдаются прямо в этой
локации — без редиректа и без пересопоставления.

**Инвариант:** в любой локации, которая переиздаёт заголовки И отдаёт SPA,
`try_files` обязан заканчиваться кодом, а не URI. Проверка одной командой:

    curl -sS -D - -o /dev/null https://hub.signaris.ru/p/test | grep -i referrer
    # ожидается: referrer-policy: no-referrer

Побочно исправилось и кэширование: было `max-age=0`, стало `no-store`.

### Сущности точек Hub и iiko НЕ связаны (решение владельца 2026-08-20)

Отчёт показывает названия точек так, как их ведёт iiko («Ветеранов д.185 к2»),
и никакого моста к `stores` не строит. Причина: сопоставление по имени — это
перевод, который однажды ошибётся и покажет управляющему выручку ЧУЖОЙ точки,
а заметить такую ошибку почти невозможно. Имя из iiko человек и так узнаёт.

**Прямое следствие, принятое сознательно: сузить отчёт до «своих» точек
нечем, поэтому владелец франчайзи видит и чужие точки.** Доступ решается
ролью, а не скоупом.

История: колонка `stores.iiko_department` (0038) с job'ом сопоставления
прожила один день и снята ревизией 0039. Если решение когда-нибудь
пересмотрят — восстанавливать надо ОБА куска (колонку и перевод UUID→строка),
а не только колонку: без перевода фильтр OLAP собрать не из чего.

### Кто видит отчёты

- **вся сеть** — hub-admin, publisher+, офис, ТУ и владельцы франчайзи;
- **403** — линейный сотрудник на точке.

Офис, ТУ и франчайзи разрешены в `app/api/reports.py::_require_report_access`
ЯВНО по `org_role`: `org_scope.resolve_scope` заведён под аналитику по
СОТРУДНИКАМ и отдаёт им скоуп по своим людям, а здесь вопрос только
«пускать или нет». Расхождение с learn-аналитикой Ф5 (там офис без
content-роли publisher получает 403) осознанное — если правило должно быть
общим, менять надо оба места.

### Инварианты

- **Модель живёт в ОТДЕЛЬНОМ systemd-юните** (`app/stt_service.py`,
  `ops/systemd/signaris-hub-stt.service`), а не в API-процессе. На машине с
  ~1,1 ГБ свободных OOM-killer выбирал бы жертву сам — среди Postgres, Redis и
  двух приложений. Тест `test_api_process_never_imports_the_model` следит,
  чтобы `faster_whisper` не просочился в основной процесс.
- **`MemoryMax` в одиночку не работает.** Первая попытка с `MemoryMax=900M`
  дала OOM сразу после загрузки: cgroup считает не только RSS (759 МБ), но и
  страничный кэш от чтения 500-мегабайтного файла весов. Нужна ПАРА:
  `MemoryHigh=800M` (мягкий порог — ядро вытесняет кэш и тормозит процесс) +
  `MemoryMax=1100M`. Разрыв между ними и есть место под кэш.
- **Выгрузка по простою обязательна.** С загруженной моделью свободной памяти
  на машине остаётся ~500 МБ; после выгрузки (5 минут простоя) возвращается
  ~830 МБ. Проверено на живом юните: 757 МБ → 425 МБ.
- **Одна расшифровка за раз** (`asyncio.Lock`): две не влезут в память и
  займут оба ядра. `CPUWeight=30` — API во время расшифровки отвечает за 50 мс
  (замерено).
- **Расшифровка идёт В ПОЛЕ, а не в отправку.** Ошибка ASR должна быть видна и
  правима до выполнения действия.
- **Микрофона нет вовсе, пока STT не настроен** (`/ai/status` отдаёт `voice`).
  Неактивная кнопка микрофона читается как сломанная, а не как «скоро».
- **`Permissions-Policy: microphone=(self)`** в `hub-security-headers.conf` И в
  каждой локации, где строка продублирована вручную. Со значением
  `microphone=()` `getUserMedia` отдаёт `NotAllowedError` независимо от
  разрешения в браузере. Проверено на staging:
  `document.featurePolicy.allowsFeature('microphone') === true`.
- **Форматы браузера декодируются из БАЙТОВ**: webm/opus (Chrome) и mp4/aac
  (Safari) читает PyAV внутри faster-whisper — ни ffmpeg, ни временных файлов.
- **Env-переменные требуют рестарта ОСНОВНОГО сервиса**, а не только нового
  юнита: `EnvironmentFile` читается при старте, и кнопка микрофона не
  появлялась, пока API держал старое `stt_enabled=False`.
- **staging-юнит собирать `ops/systemd/make-staging-unit.py`**, а не sed'ом.
  Правка «в уме» трижды дала юнит, который назывался staging, а смотрел в ПРОД
  (BSD-sed не знает `\b`; `WorkingDirectory` идёт без слеша на конце; номер
  порта встречается в комментарии). Скрипт делает проверку невозможной к
  пропуску.

### Память VPS: сборка фронта против STT (найдено при выкатке 2026-08-20)

`vite build` на сервере требует ~1 ГБ, машина 1,9 ГБ, и с поднятым STT-юнитом
сборка **была убита OOM'ом**. Хуже самого падения было то, как оно выглядело:
`deploy.sh` отрапортовал успех, на сервере остался ПРЕЖНИЙ dist, и заметить
это можно было только по `version.json`.

Закрыто в `deploy/deploy.sh`: перед сборкой юнит останавливается

упала), а сама сборка проверяется на `dist/index.html` и при неуспехе деплой
падает с внятным сообщением и подсказкой смотреть `dmesg`.

**Одна STT-машина на хост.** Два юнита (прод + staging) 1,9 ГБ не тянут:
каждый в простое держит ~300 МБ, с загруженной моделью — 760 МБ. Сейчас
включён ПРОД (`signaris-hub-stt`), staging-юнит `disable`-нут. Переключение —

## Маркер окружения и «грузим» vs «пусто» (2026-08-19)

Первопричина: час ушёл на разбор «на iPhone пропали проекты, на Mac они есть». Телефон смотрел **staging**, десктоп — прод. На staging все проекты лежат в тенанте `signaris`, а вход был под `pp@uppetit.ru` (тенант `uppetit`) → RLS вернул `[]` с кодом 200, и UI честно нарисовал пустое состояние. Багов в правах не было; отличить среды было нечем.

- **Прод бэкенда зовётся `prod`, прод сборки — `production`.** На VPS `SIGNARIS_HUB_ENVIRONMENT=prod`, а vite mode даёт `production`. Оба значения обязаны считаться продом — источник истины `PROD_VALUES` в `web/src/lib/appEnv.ts`. Проверка против одного написания зажгла бы маркер на боевом домене. Плюс `app/config.py` имеет дефолт `environment='staging'`: прод без своей env-переменной покажет маркер, и это осознанно (среда действительно сломана).
- **Маркер опирается на build-mode, `/api/env` — второе плечо.** `__APP_MODE__` известен синхронно (маркер есть на первом кадре, без запроса), а `environment` с бэкенда ловит «прод-сборку руками положили на staging». Значение бэкенда кладёт bootstrap в `main.tsx` — он и так тянет `/api/env` до первого рендера ради Sentry, нового запроса нет.
- **Имя ярлыка на iOS берётся из `apple-mobile-web-app-title`, а НЕ из манифеста.** Правка одного манифеста была бы no-op ровно на iPhone. Оба места переименовывает плагин `hub-env-title` в `web/vite.config.ts` — точечной заменой двух строк index.html, **тело анти-FOUC скрипта не трогается**: его sha256 в CSP (`ops/nginx/hub-security-headers.conf`). Плагин падает на сборке, если якорь не найден, — иначе переименование тихо перестало бы работать. Уже установленная иконка на iOS сохраняет старое имя до переустановки.
- **`EnvChip` монтируется в `main.tsx`, не в `Shell`.** Так он покрывает `/login`, `/auth/callback` и публичную `/p/:token` (все вне Shell) и гарантированно не попадает внутрь `.glass`-предка: `backdrop-filter` создаёт containing block и превращает `fixed` в `absolute` (так ломался `DragOverlay`). Слои: чипу `z-30` — ниже шторок и диалогов (`z-50`) и баннера обновления (`z-40`); `pointer-events-none` обязателен, иначе чип съедает тапы по строке под собой. Отступ снизу — по формуле safe-area, как у FAB, иначе на iPhone уезжает под таб-бар.
- **Всплывашки не имеют права садиться на мобильный таб-бар.** Он `fixed bottom-0` и является ОСНОВНОЙ навигацией. Тосты sonner ниже 600px растягиваются во всю ширину и до 19.08 ложились прямо на него, а баннер обновления делал это же и висел до нажатия «Позже», то есть блокировал переходы. Теперь: тосты — `position="top-right"` с `mobileOffset`, включающим `env(safe-area-inset-top)` (у sonner СВОИ мобильные отступы, и без safe-area в PWA тост уехал бы под часы — зеркало той же ошибки сверху); баннер остался снизу, но поднят над таб-баром по формуле FAB через `useIsDesktop()` — инлайн-стиль перебил бы класс `bottom-4` на всех ширинах, а `sm:` не годится: таб-бар живёт до `lg`. Баннер НЕ переносим наверх: он персистентный и закрыл бы шапку с переключателем пространств — единственным выходом из «Обучения» на телефоне.
- **Ручное обновление (`useAppUpdate`) работает на штатных SW-API, а не на втором `useRegisterSW`.** Второй экземпляр хука завёл бы собственную регистрацию и второй набор колбэков рядом с `UpdateBanner`. `SKIP_WAITING` обрабатывает `web/src/sw.ts` — тот же путь, что у баннера. Две тонкости, без которых кнопка врёт: `registration.update()` резолвится, когда воркер только НАЧАЛ устанавливаться, поэтому `waiting` надо дождаться (иначе почти всегда «у вас последняя версия»); а `controllerchange` в PWA на iOS может не прийти вовсе — поэтому перезагрузка по таймауту, иначе кнопка зависает навсегда. Поверхностей две и обе обязательны: футер «Настроек» (десктоп) и строка в «Профиле» (на телефоне в Настройки за версией не ходят).
- **Список запросов: `isLoading → isError → пусто → список`, именно в этом порядке.** До 19.08 блок «Проекты» на главной (обе витрины `HomePage.tsx`) во время загрузки писал «Проектов ещё нет. Нажмите «+» внизу» — то есть утверждал факт, которого ещё не знал. Ветку `isError` нельзя ставить после проверки на пустоту: ошибка снова читалась бы как «проектов нет». `isLoading` в TanStack v5 — только первая загрузка, поэтому `refetchOnWindowFocus` скелетон не мигает (проверено в браузере).

## ОС 17.08 — множественные исполнители + папки проектов (2026-08-18)

Два фиче-реквеста тестировщика UPPETIT (багов в отчёте не было). Инварианты, которые легко сломать при следующей правке:

- **`task_assignees` — источник истины по исполнителям (0034).** `tasks.assignee_id` оставлен как deprecated-зеркало первого исполнителя (position=0) и удаляется отдельной ревизией **0035-drop** (пока не написана). Причина expand/contract: `deploy.sh` делает `rsync → pg_dump → pip install → alembic upgrade → systemctl restart`, то есть СТАРЫЙ процесс работает всю миграцию — `DROP COLUMN` уронил бы в `UndefinedColumn` любое чтение задач на всё окно `pip install`, и `systemctl restart` на предыдущий билд перестал бы быть рабочим откатом.
- **Единственный писатель зеркала — `app/services/task_assignees.py`.** На ревью грепать: `Task.assignee_id =` и `assignee_id=` в конструкторе `Task(` не должны встречаться нигде, кроме этого модуля (и тестовых фикстур, конструирующих `Task` напрямую — например `tests/integration/test_stats_search.py`). Присваивать ТОЛЬКО ORM-атрибутом: Core `update()` оставит объект в сессии протухшим, и сериализация в том же запросе вернёт старое значение.
- **`task_assignees` в списочных запросах — только `EXISTS` (фильтр) или отдельным батч-запросом (отображение).** Наивный JOIN размножит строку задачи по числу исполнителей: дубли карточек на доске, поехавший `ORDER BY …, Task.position`, съеденные `_GROUPED_LIMIT`/`_WORKLOAD_TOP`. Единственное исключение — `stats._workload`, где фан-аут НАМЕРЕННЫЙ (задача на двоих считается обоим), из-за чего сумма по строкам дашборда «Загрузка» БОЛЬШЕ числа задач, а бакет «без исполнителя» считается отдельным запросом и склеивается ПОСЛЕ `limit`.
- **Валидация всего списка исполнителей — ДО любых записей и ДО `_allocate_task_seq`** (тот держит row-lock проекта до конца транзакции). Иначе 404 на третьем исполнителе оставит первых двух записанными.
- **`set_task_assignees` звать строго ПОСЛЕ `db.flush()`** для новых задач — FK `task_assignees.task_id` требует, чтобы строка задачи уже была в Postgres (та же ловушка, что с `record_activity`).
- **PATCH `assignee_ids` — replace-семантика (last-writer-wins по всему набору).** Поэтому UI ходит в инкрементальные `POST /tasks/{id}/assignees` и `DELETE /tasks/{id}/assignees/{employee_id}`: с набором «двое правят одновременно» перестало быть экзотикой, а потеря добавленного была бы беззвучной. PATCH остаётся для легаси-`assignee_id` старых PWA-бандлов и bulk-замены. Следствие, о котором предупреждён тестировщик: старый бандл, приславший `assignee_id: null`, снимает ВСЕХ.
- **Activity `assigned` сохранил kind** (новый провалился бы в `default:` старых бандлов) и несёт и новый формат (`added`/`removed`/`*_names` — снапшот имён), и легаси-зеркала `old`/`new`. Рендер в `TaskThread` ветвится по `Array.isArray(p['added'])`.
- **Фронт читает исполнителей ТОЛЬКО через `taskAssignees()`** (`web/src/lib/taskAssignees.ts`): прямое `task.assignees.map()` падает на объекте из react-query-кэша, пережившего деплой, и на ответе откаченного бэка. Модуль отдельный от `lib/tasks.ts`, потому что тот тянет `api → auth → window`, а vitest в проекте бежит без jsdom.
- **`useUpdateTask.onMutate` кладёт в кэш ровно тело запроса** — для полей, которых в теле нет (`assignees` против `assignee_ids`), заведён люк `__optimistic`, ОБЯЗАТЕЛЬНО отрезаемый в `mutationFn`.
- **Папки проектов — общие для тенанта, ровно один уровень.** CRUD — гейт `can_manage_project_folders` (= `can_create_project`, hub admin|member); перенос проекта — `require_project_role(allow=("owner",))`, поэтому фронт гейтит контролы по уже существующему `can_manage` и своей копии правила не заводит. Удаление папки НИКОГДА не удаляет проекты (`ON DELETE SET NULL`).
- **`ProjectFolderListResponse` не отдаёт `project_count`** — он был бы tenant-wide и расходился бы с видимым пользователю списком, плюс утечка «есть проекты, которые тебе не показывают». Считает клиент.
- **FK `projects.folder_id` НЕ проверяет совпадение тенантов** (RI-триггеры Postgres обходят RLS). Единственная защита — `db.get(ProjectFolder, ...)` через tenant-scoped сессию перед присваиванием.
- **`useDraggable`: `transform` на узле ИЛИ `DragOverlay` — но развилка обязательна.** Без оверлея (`ProjectListPage`, `CalendarTaskBar`) `transform` ОБЯЗАТЕЛЕН: без него карточка не едет за курсором, её rect не смещается, collision detection не видит дропзону и дроп молча не срабатывает. С `DragOverlay` (сайдбар) — наоборот, `transform` ставить НЕ надо: коллизии считаются по rect оверлея, а transform внутри `overflow-y-auto` обрезался бы границей контейнера. Не «чинить» одно по образцу другого.
- **`DragOverlay` нельзя рендерить внутри элемента с `backdrop-filter`.** `.glass` (`brand.css:159`) создаёт containing block для `position: fixed`, которым и является оверлей — внутри `<aside className="glass">` он смещается и обрезается границами сайдбара, что выглядит как «перетаскивание не работает». В `Sidebar.tsx` оверлей — СОСЕД `<aside>` внутри `DndContext`. Если сайдбар когда-нибудь завернут в трансформируемую шторку — переезжать на `createPortal(…, document.body)`.
- **dnd-id должен быть уникален на элемент, а не на сущность.** В сайдбаре один проект рендерится дважды (в «Избранном» и в своей папке); `useDraggable` кладёт узел в `draggableNodes.set(id, …)`, вторая регистрация перетирает первую, `isDragging` (= `active.id === id`) срабатывает у обеих строк, а `data` приходит от смонтированной последней. Отсюда `projectDragId(scope, id)` в `web/src/lib/projectDnd.ts` — id вида `fav:<uuid>` / `group:<uuid>`, а `onDragEnd` читает только `data`, id не парсит.
- **`pointerWithin` вместо дефолтного `rectIntersection` для вертикального стека дропзон** (`Sidebar.tsx`): на границе двух групп «по площади перекрытия» превращается в лотерею, а вне зон `pointerWithin` не возвращает ничего — случайный дроп мимо ничего не двигает. Цена: зоны обязаны стыковаться без зазоров, поэтому у групп `py-1`, а не `space-y-*` у контейнера.
- **Папку можно создать из трёх мест** (ОС 18.08 «не могу обнаружить создание папки»): шапка `/projects`, меню «Создать» в сайдбаре и «+» у заголовка «ПРОЕКТЫ». Диалог общий — `web/src/components/project/CreateFolderDialog.tsx`, id поля через `useId` (страничный и сайдбарный экземпляры существуют параллельно). Гейт везде один — `can_manage` из `GET /project-folders`; своей копии правила фронт не заводит.
- **Пустые ИМЕНОВАННЫЕ папки в сайдбаре теперь видны всегда** (изменено 18.08, отменяет прежнее «пустые папки скрыты»). Причина: папку создают прямо из сайдбара, и она обязана быть видна там, где создана, — иначе это читается как «создал, а её нет». Прячется только пустая группа «Без папки»: её заголовок с нулём — шум (во время драга он нужен как зона «вынуть из папки»).
- **Мобильная навигация между пространствами: `SpaceSwitcher` обязан быть в шапке ОБЕИХ витрин и в learn-«Меню».** До 18.08 он рендерился только в `HomePage` (задачи) — попав в «Обучение» с телефона, выйти было нельзя вообще: десктопный сайдбар там не рендерится, а в `LearnMenuSheet` переключателя не было. Навигационная ловушка на проде. Теперь переключатель есть в шапке `LearnHomePage` (`lg:hidden`) и первым блоком в «Меню», доступном с ЛЮБОГО learn-экрана.
- **Закрывать `BottomSheet` при навигации нужно по ВСПЛЫТИЮ, не в capture.** `onClickCapture` размонтирует лист раньше, чем отработает `onClick` кнопки внутри, — навигация не происходит вовсе (поймано браузерной проверкой при первом заходе на фикс выше).
- **`FloatingActionButton` — ЕДИНСТВЕННАЯ кнопка создания на мобильном** (`lg:hidden`, монтируется на главной и «Моих задачах»). Всё, что можно создать, обязано быть в её шторке: сайдбарное меню «Создать» на телефоне не существует. Сейчас там Задача / Проект / Папка.
- **`Sidebar` рендерится только при `≥1024px`** (`Shell.tsx:96`, `useIsDesktop`). Любая функциональность, добавленная только в сайдбар, для мобильных пользователей не существует — на телефоне единственный вход в папки — шапка `/projects`, куда попадают ссылкой с «Главной» (вкладки «Проекты» в таб-баре нет).
- **`Button` не имеет `whitespace-nowrap` и `shrink-0`** при фиксированной `h-9`: две текстовые кнопки в шапке на 390px не помещаются, текст переносится и вылезает за границы. В шапке `/projects` до `sm:` кнопка «Новая папка» иконочная, «Новый проект» с укороченной подписью, заголовку — `min-w-0` + `truncate`. Тот же приём понадобится любой другой паре кнопок в шапке.
- **Сбой `GET /project-folders` больше не молчит.** Раньше при ошибке `data` был undefined → `can_manage` falsy → кнопок просто нет, что внешне неотличимо от «нет прав» и от «фичи не существует». Теперь и в сайдбаре, и на `/projects` рендерится строка ошибки с «повторить».
- **Авто-разворота свёрнутой папки при наведении сознательно НЕТ.** Разворот меняет высоту группы, её `ResizeObserver` ставит в очередь только свой id, а группы ниже сохраняют закэшированный rect — дроп уехал бы на высоту раскрытого списка. Если понадобится: `measureDroppableContainers()` из `useDndContext()` без аргументов в `requestAnimationFrame` после разворота + отдельный `expand(id)` в сторе (`toggle` схлопнет уже открытую).
- **Ловушка на ревью вёрстки:** `group-hover` требует класс `group` на ОБЩЕМ предке; кнопка «…» — сосед `<Link>`, а не его потомок. Плюс на тач-устройствах hover'а нет — контрол должен быть видим без него (`md:opacity-0 md:group-hover:opacity-100`).

## ОС 12.08 — санитайзер rich-контента и авторский UX (2026-08-12)

Блок правок редактора уроков по второй волне ОС тестировщиков (нумерованный список 422, паста с форматированием, таблицы, размеры текста, публикация из редактора, удаление курса из списка, опрос из урока).

**ИНВАРИАНТ: клиентский санитайзер зеркалит серверный whitelist — менять ПАРОЙ.** `web/src/components/learn/rich/sanitizeRichDoc.ts` (`NODE_ATTRS`/`MARK_ATTRS`) — зеркало `app/services/rich_content.py`; правишь один — правь второй и оба набора тестов (`sanitizeRichDoc.test.ts` + `tests/unit/test_rich_content.py`) на ОДНИХ фикстурах реального вывода TipTap 3.28. Первопричина всего класса багов: TipTap сериализует ВСЕ schema-attrs включая дефолты (`orderedList.type: null`, `tableCell.align`), а fail-closed валидатор отвечал 422 на весь PATCH. Второй подвид того же класса (пойман браузерной проверкой на staging): parseHTML пасты даёт **пустые строки** — `<span style="color:…">` без font-size получает `fontSize: ''` → санитайзер дропает и null, и `''`; сервер трактует `''` как отсутствие (textStyle.color/fontSize, highlight.color). Санитайзер вызывается на выходе редактора (getJSON→sanitize→onChange), editor-state не мутируется (undo цел); lesson-ноды (`LESSON_NODE_TYPES`) проходят НЕТРОНУТЫМИ — иначе развернулись бы в параграфы и `checkQuestion.attrs.correct` потерялся бы.

Остаточные упрощения v1:
- **Таблицы без merge/split UI** (`resizable: false`, только +/− строк/колонок и шапка) — но рендер colspan/rowspan/align в `RichRenderer` есть (шаблоны с merge-ячейками не едут).
- **Word-списки `type='a'`** деградируют в цифровую нумерацию (клиент дропает `type`; сервер атрибут допускает, рендер игнорирует).
- **Опрос-черновик, встроенный автором в урок**, до публикации publisher'ом не открывается сотруднику — автору показывается тост-предупреждение; инлайн-статус опроса в рендере урока не делали.
- **fontSize** — только px из фиксированного набора 12..32 (сервер допускает `^\d{2}px$`, 10..48).
