# Architecture

## Принципы

1. **Единая авторизация.** Никакого собственного логина — только SSO через [auth.signaris.ru](https://auth.signaris.ru) по чек-листу `CentralAuthService/client-libs/INTEGRATION.md` (13 шагов + §14 deletion-sync). Без per-product «снежинок».
2. **Multi-tenancy через RLS.** Каждая бизнес-таблица — `tenant_id UUID NOT NULL` + Postgres-policy. Приложение работает от non-superuser-роли (RLS реально enforced), миграции — от migrate-роли (BYPASSRLS).
3. **Shadow-таблицы.** `shadow_tenants` + `shadow_users` (с `deleted_at TIMESTAMPTZ NULL`) апсертятся на каждый authenticated-запрос. Доменные FK ссылаются на `shadow_users.employee_id` — не на JWT.sub.
4. **Deletion-sync.** Воркер `run_deletion_sync_worker` (lib ≥ 0.8.0) в lifespan тянет события из `auth.signaris.ru/api/products/deletions`; курсор — `sync_state(key='deletion_sync')`. `_on_event`: `employee_deleted`/`transferred` → `archive_profile(auth_deleted)`, `employee_updated` → `_apply_rename` (вторая копия имени в `employee_profiles`); **no-op только для task-домена** — история тасков сохраняется, списки сотрудников фильтруются `WHERE shadow_users.deleted_at IS NULL`.
5. **Staff-sync (0052, «auth — источник штата», прод 04.09).** Pull-воркер `app/services/staff_sync.py` (15 мин + кнопка «Обновить из auth», отдельный ключ `SIGNARIS_HUB_STAFF_SERVICE_KEY`) тянет `GET /api/products/employees?product=hub` (контракт — `docs/handoffs/HUB_TASK_staff_endpoint_REPLY.md`): тени + кеш `hub_role/auth_active/staff_synced_at` всем строкам; учебная карточка — только `account_kind=person` с ролью и `is_active` (service-строкам — привязка существующей, `link_only`), архивный email блокирует создание; снапшот `auth_invitations`; sweep ролей на полном снимке. INSERT теней здесь легален — pull-bootstrap, не фид. Staging выключен навсегда (общий VAPID). Подробно — `docs/ROLES.md` §«Откуда Hub знает штат» и hot-бюллет CLAUDE.md. **С 16.09 auth — единственный источник карточек:** ручное заведение и создание CSV-импортом закрыты (писателей `employee_profiles` два — первый вход и синк), импорт только обновляет HR-поля существующих карточек по email, статус учётки считается одной функцией `services/auth_state.py` и знает `invited` по зеркалу `auth_invitations`.
6. **Зеркало реестра объектов (0053, sites-sync, прод 05.09).** Auth ведёт справочник точек `sites`; Hub держит `shadow_sites` (RLS, `refs` JSONB — допускает несколько ссылок `system=hub` на объект: наши 4 пары дублей) и `stores.site_id` (UUID без FK, заполнен разовым бэкфиллом из файла связей — не API и не синком). Синк `app/services/sites_sync.py`: полный снимок БЕЗ пагинации, сверка `len(items)==total` до записей, replace по-тенантно под `pg_try_advisory_xact_lock`; с 19.09 — ежечасная джоба `app/jobs/sites_sync.py` (`:10`) и ручной `POST /api/learn/sites/sync`. **Применение реестра к `stores` (`services/registry_apply.py`, решение владельца 19.09: реестр — источник истины про точки):** после снимка живой объект с iiko-ссылкой без карточки → карточка создаётся из реестра; архивный объект → карточка архивируется (`reason=registry`, `rebuild_tenant` + уведомления, как ручной архив); разархивация только руками (асимметрия); стоп-правило — непривязанная живая карточка с тем же кодом или нормализованным именем → объект ждёт человека (`GET /learn/sites/pending`, блок в Оргструктуре), объект без iiko-ссылки — тоже; объект с любым магазином (в т.ч. 4 пары дублей) автоматика не трогает. Ручная привязка — `site_id` в `StoreCreate/StoreUpdate` (422/409). Занятые try-локом тенанты применение пропускают: план по старому зеркалу был бы планом по прошлому. **Зеркало полей (0059):** `stores.registry_name/code/address` = последнее применённое значение реестра; поле карточки следует за реестром, пока равно ему или пусто (`registry_apply.field_changes`), поэтому карточки, рождённые из реестра, идут за ним, а 59 бэкфилленных сохраняют короткие имена Hub и получают только адрес; запись каждой карточки под `begin_nested()` — конфликт `uq_stores_active_name` считается, не роняет прогон. **Слияние дублей — `services/store_merge.py`:** узкий инструмент для живых карточек одного `site_id` (четыре пары с 28.08); `plan_merge` считает, что перейдёт (сотрудники, группы/ТУ с дедупом, смены, `audience_rules.store_ids` через `array_replace`+дедуп, снапшоты опросов, участие/базы/снимки/итоги гонки по правилу «победитель богаче»), `recommend_winner` — по людям, участию в гонке, возрасту; `apply_merge` одной транзакцией, проигравшая — в архив с `site_id`, `rebuild_tenant` + уведомления; ручки `GET /learn/org/stores/{id}/merge-preview?into=` и `POST /learn/org/stores/{id}/merge`. После слияния Hub отдаёт auth список `site_id → архивированная карточка`, auth снимает мёртвые `hub`-ссылки. Чтение `GET /api/learn/sites` — строго hub-admin (ИНН/юрлица; `org_snapshot` открыт всем). Три состояния связи (`web/src/lib/siteLink.ts`): none/live/stale (строки нет или снимок старше 14 фикс-суток). Скоуп отчётов iiko: franchisee_owner видит только свои точки — фильтр `Department.Id` из `refs`, кэш-ключ отчёта включает скоуп, ноль привязок → 409, writeoff франчайзи → 409 (TRANSACTIONS не отдаёт Department.Id). Полные числа приёмки — `docs/handoffs/HUB_TASK_sites_mirror_REPLY.md`.

## Backend

- **FastAPI** async + lifespan: JWKS-warmup, Redis pool, фоновые воркеры deletion-sync, staff-sync и sid-sync (все через `worker_supervisor.supervise` — рестарт с backoff + Redis leader-lock), Sentry init (опц.). In-memory store sid-sync блокирует `--workers > 1` (см. TECH_DEBT).
- **`tenant_scoped_session(tenant_id, *, bypass_rls)`** — async ctx manager (`app/db.py`), паттерн CentralAuthService (post-`3cfb256`). Помечает сессию `session.info["rls_scope"]`; листенер `_apply_rls_on_begin` (`after_begin`) ставит `app.tenant_id`/`app.bypass_rls` через `SET LOCAL` на старте каждой транзакции (переживает mid-request commit + смену соединения в пуле — session-level вариант дал кросс-tenant утечку 2026-08-01, см. TECH_DEBT). Для lib-воркеров с сырой фабрикой — `bypass_session_factory()`.
- **`require_auth = build_require_auth(verifier)`** — `signaris-auth-client.TokenVerifier` валидирует RS256-JWT по JWKS. Никакой собственной валидации.
- **Shadow upsert middleware** — после `require_auth`: `upsert_shadow_tenant(db, principal)` + `upsert_shadow_user(db, principal)` + commit.

## Frontend (PWA)

- **React 18 + TS strict** + Vite + `vite-plugin-pwa` (`registerType: 'prompt'`, `strategies: 'injectManifest'`).
- **Auth:** `createSsoAuthClient({...})` из `@signaris/auth-client/browser` + `attachAxiosAuth(api, authClient)`. Refresh-token — в IndexedDB (PWA standalone), access-token — в памяти через zustand.
- **Service Worker:** `web/src/sw.ts` — precache + push handler + notificationclick + SKIP_WAITING-message.
- **Update mechanism:** `UpdateBanner.tsx` проверяет SW каждые 60с + на `visibilitychange` — лечит iOS PWA-freeze таймеров в фоне.

## Сущности

### Контейнеры
- `Workspace = tenant_id` (из JWT, без своей таблицы)
- `projects` (id, tenant_id, key, name, description, archived_at, created_by, personal_owner_id)
  - `personal_owner_id` (0042) — личное пространство сотрудника «Личное»: NULL у обычных проектов, partial UNIQUE `(tenant_id, personal_owner_id)`. Проект скрыт из ВСЕХ списков (предикаты `app/services/personal_projects.py`), заводится идемпотентно в `GET /api/me`; в чужом личном участник видит только свои задачи. Инвариант целиком — CLAUDE.md §«Задачи и проекты»
- `project_members` (project_id, employee_id, role: `owner` | `editor` | `viewer`)
  - Права фронту отдаёт сервер: `project_access.capabilities()` → `ProjectResponse.can_edit/can_manage` (hub-admin вне членства тоже правит); фронт роли не вычисляет.
- `sections` (project_id, name, position)

### Задачи
- `tasks` (project_id, parent_task_id, title, description markdown, done BOOLEAN + completed_at под CHECK, priority: `low` | `medium` | `high` | `urgent`, start_at, due_at, position NUMERIC, search_vector tsvector).
  - Подзадачи только 1 уровень — CHECK `parent_task_id IS NULL OR (SELECT parent_task_id FROM tasks t2 WHERE t2.id = parent_task_id) IS NULL`; UI — секция в карточке (SubtaskList), в топ-уровне List/Board не показываются
- Инструкции по работе в Hub — не сущность БД: две готовые HTML-страницы в `guides/` (репо) отдаются `GET /api/guides/{kind}?e&s` по подписи (`services/guides.py`, тот же `issue_token`, что у медиа) через internal-локацию nginx. Кому какая — `guides_for_role` (hub-admin: обе, остальные: сотрудницкая), ссылки приходят готовыми в `GET /api/me`. Первая задача сотрудника («Изучите инструкцию») заводится в момент создания личного проекта — `services/onboarding.py`, вызов в `ensure_personal_project`
- `POST /api/feedback` — обратная связь из настроек: текст + необязательный файл → задача в проекте по ключу `SIGNARIS_HUB_FEEDBACK_PROJECT_KEY` (первая колонка, метка «Обратная связь», исполнитель — владелец проекта, пуш ему). Открыта любому сотруднику: rate-limit 5/час; с 02.09 автор ПОДПИСЫВАЕТСЯ наблюдателем и получает viewer-членство в проекте обратной связи явными шагами (`ensure_watcher(reason="creator")` + `ensure_project_member`; `watch_creator=False` остался — побочки create молчат и членства не дают); проверки файла — общий `services/attachments.py::store_upload`. Детали и причины — `app/services/feedback.py`.
- `project_stages` (project_id, name, position; 0040, свободные с 0044) — колонки доски: ТОЛЬКО имя и позиция, системного смысла нет. `tasks.stage_id` НЕОБЯЗАТЕЛЕН (0046): `NULL` = «без статуса» — задача есть в списке, календаре, поиске и `/me/tasks` (там `outerjoin`), но не на доске; новая задача без явного `stage_id` уходит в первую колонку. FK без `SET NULL`: удаление колонки с задачами требует выбора — `move_to` (перенести) или `detach` (оставить без колонки), без обоих 409. Колонок у проекта может не быть вовсе (26.08): новый проект рождается пустым, и удалить можно любую колонку, включая последнюю; состояние задачи — независимая ось `tasks.done`, пишет её только `app/services/stages.py::set_done`. API `app/api/stages.py`
- `tasks.seq` (0032–0033) — номера «KEY-42» внутри проекта, выдача только `allocate_task_seq` под row-lock проекта; `project_id` меняется ровно одним путём — переносом (ниже)
- `task_assignees` (task_id, employee_id, position, assigned_by; PK составной, RLS с 0034) — **единственное место, где живут исполнители**; колонка-зеркало `tasks.assignee_id` удалена ревизией 0036. Пишет только `app/services/task_assignees.py`; в списках — EXISTS/батч, не JOIN

- `task_comments` (markdown, `mentioned_ids UUID[]`)
- `task_labels` (name, color) + `task_label_assignments` (с tenant_id и RLS с миграции 0011); API `app/api/labels.py`, чипы в List/Board/drawer, фильтр
- `task_attachments` (whitelist mime без SVG, 20 MB)
- `task_activity` (append-only event log)
- `task_dependencies` (predecessor/successor, finish-to-start, BFS cycle-check `app/services/dependency_cycle.py`, миграция 0010) — стрелки на Timeline
- `custom_field_definitions` + `task_custom_field_values` (7 типов, миграция 0007) — колонки List, агрегаты Dashboard
- `public_share_tokens` (scope task|project, БЕЗ RLS — cross-tenant lookup по токену, миграция 0009) — view-only `/p/{token}`
- `project_members.is_favorite` (миграция 0012) — личное избранное, секция в Sidebar

### Перенос задачи между проектами (28.08)

`POST /tasks/{id}/move` + `GET /tasks/{id}/move-preview`, обе — `app/api/tasks.py`, работа — `app/services/task_move.py`.

**Почему отдельная ручка, а не поле в PATCH.** На `TaskUpdate` стоит `extra="forbid"` (0045) — вчерашний PWA-бандл получил бы 422 вместо no-op; `update_task` расширяет права до viewer'а для `ASSIGNEE_EDITABLE_FIELDS`, и переносу там не место; ответ PATCH по инварианту не несёт `can_complete`, а переезд обязан вернуть новый ключ.

**Почему план и исполнение — две функции.** `plan_move` считает, `apply_move` раскладывает посчитанное. Предпросмотр в диалоге и сама запись идут по ОДНОМУ коду: вторая реализация правил «что переедет» разошлась бы с первой на первой же правке. `dry_run` «сделать и откатить» (как у импорта CSV) не подошёл: `allocate_task_seq` инкрементит `projects.next_task_seq` до отката, и диалог, где человек перебирает пять целей, оставил бы дыру в каждой. `plan_move` не пишет ничего, `new_key` у предпросмотра — `null`.

**Что делает переезд.**

| | правило и причина |
|---|---|
| номер | новый, через `allocate_task_seq` цели — `uq_tasks_project_seq` иначе падает. Старый ключ уходит в ленту (`kind="moved"`, payload `from_key`/`to_key`/`from_project`/`to_project`) — это единственный его след, ссылки «PLP-118» в переписке больше не сходятся |
| семья | подзадачи едут за родителем, нумеруются по возрастанию старого `seq`. Одна подзадача — 409: `parent_task_id` — FK на `tasks.id` без проектного ограничения, БД разрыв стерпит, а `SubtaskList` ищет детей в списке нового проекта и покажет ноль |
| позиция | `next_position(db, target, stage_id=…)` каждой переехавшей. Позиция — `max+1` внутри (проект, колонка), и число из чужой шкалы поставило бы задачу в середину списка |
| колонка | у корня — из запроса (`None` = «без статуса», 0046), у подзадач — по совпадению ИМЕНИ, через `.get()` а не индекс. Оставить `stage_id` как есть нельзя: FK на `project_stages` проектом не ограничен и намеренно без `SET NULL` — строка сохранится, а на доске цели задача не появится никогда |
| метки | по точному совпадению имени; новых меток в цели не заводим — перенос задачи не должен править справочник чужого проекта |
| кастом-поля | по паре (имя, ТИП): по одному имени число уехало бы в текстовое поле. `select`/`multi_select` пересобираются по ЛЕЙБЛУ опции (id у одноимённых полей свои), финальный фильтр — `custom_field_validator.validate` |
| исполнители | `ensure_project_member(viewer)` в цели — иначе человек узнает о переносе по 403 из пуша |
| наблюдатели | не ставшие участниками — отписываются, их `notifications` по задаче удаляются. Членство в ЦЕЛИ перенос не раздаёт: доступ в целевой проект — решение его редакторов, а не побочка переноса (с 02.09 редактор может подписать человека обратно вручную — `POST /tasks/{id}/watchers` выдаёт viewer-членство явно). Исключение — САМ переносящий: права редактора в цели у него только что проверены, и без оговорки админ отписывался от собственной задачи (найдено на staging 28.08) |
| зависимости | связи со вторым концом в старом проекте удаляются: `api/dependencies.py` отвечает 400 на кросс-проектные, и переезд не должен оставлять на данных то, чего ручка не создаёт |
| уведомления | `url` переписывается на новый проект (`services/notify.py` кладёт туда `project_id` на момент отправки) |
| публичная ссылка | `scope=task` переехавших ОТЗЫВАЕТСЯ. `api/public.py::_build_task_view` проект не смотрит вовсе, поэтому переезд в личное сделал бы личное публичным в обход `assert_not_personal`. `public_share_tokens` — одна из четырёх таблиц БЕЗ RLS, `tenant_id` в условии обязателен |

**Права и запреты.** Редактор в ОБОИХ проектах (`require_task_access` + `require_project_role`), задача берётся `FOR UPDATE` (два одновременных переноса иначе выдали бы два номера и один отчёт-обманку). **Личный проект с любой стороны обязан быть своим** — иначе 409, в том числе hub-admin'у: его пропускает и `require_project_role` (админ-байпас), и `personal_task_scope` (для админа возвращает `None`). Цель архивная — 409, тот же проект — 400. Предпросмотр — свой bucket `task:move-preview` (60/мин): в общем `task:write` перебор целей в диалоге упирался бы в 429 на следующей правке задачи.

**Отчёт `TaskMoveReport`** несёт счётчики (`labels_kept`/`labels_total`, `values_*`, `watchers_dropped`, `dependencies_dropped`, `shares_revoked`, `subtasks`) и флаг `target_public` — у цели активна ссылка `scope=project`, а `_build_project_view` отдаёт анонимам ВСЕ задачи проекта, то есть приехавшая станет публичной без «явного акта над ней».

**Ассистенту инструмента переноса не дано** — по той же причине, что и `delete_task`: нужны права в двух проектах, и результат необратимо меняет номер.

**Фронт.** Строка «Проект» первой в свойствах карточки (обе раскладки; с 16.09 имя — ссылка на страницу проекта через `lib/taskLinks.ts::projectLocation`, стрелка ⇄ — перенос), `components/task/MoveTaskDialog.tsx` на `ResponsiveDialog`, чистые `lib/taskMove.ts` (`moveTargets` — цели, `describeTaskMove` — текст по отчёту сервера). Карточка считает проект от `task.project_id`, а НЕ от пропа страницы, и после переноса уводит на `/projects/{новый}?task=`. Мутация `useMoveTask` инвалидирует десять корней кэша предикатом: переезд меняет два проекта, и перечисление ключей по одному гарантированно что-нибудь забудет. Массовая разноска по меткам осталась за одноразовой джобой `app/jobs/split_project_by_labels.py`.

### Экран «О проекте», профиль, бейдж и удаление проекта (0049; вынесено из CLAUDE.md 07.09 по размерному предохранителю)

- **Экран «О проекте» (0049, два режима с 27.08)** — вкладка после «Участников». По умолчанию **карточка чтения**: бейдж, имя, сводка (`InfoRows`: ключ, задач, выполнено, создан, участников, владелец) и описание markdown'ом. Правка, импорт, архив и удаление — под кнопкой **«Настройки проекта»** на том же экране; режим держит локальный `useState`, а НЕ параметр URL (ссылка `?edit=1` наблюдателю была бы обещанием, которое приложение обязано нарушить). **Все шесть правил «кто что видит» считает одна чистая функция `lib/projectAbout.ts::projectAboutGate`** — два из них не выводятся из ролей (архив и удаление недоступны личному проекту, импорт — архивному), и в JSX такие правила гниют молча. ### Повтор задач (0055, 14.09)

Запрос сотрудницы «кнопка Повтор на даты задачи»; в WEEEK повторы были на 601 задаче и потерялись при переносе. Модель — **«следующая копия при выполнении»** (решение владельца): ночных джоб нет, заброшенная серия останавливается сама.

**Две сущности с разным смыслом.** Строка `task_recurrences` (PK `task_id`, поля `freq`/`step`/`anchor`/`occurrence`) = «задача повторяется ДАЛЬШЕ»; колонка `tasks.recurrence_parent_id` = «задача РОДИЛАСЬ по повтору вот этой» и остаётся у закрытых копий как история. У колонки `ON DELETE SET NULL` (не CASCADE, в отличие от соседнего `parent_task_id`) и partial-UNIQUE — одна задача не может породить двух потомков.

**Идемпотентность — через токен.** `services/task_recurrence.py::claim_rule` делает `DELETE … RETURNING`, и правило вставляется уже для копии. Снять галочку и закрыть снова нечего: токена на исходной задаче нет. Гонку двух вкладок закрывает row-lock самого DELETE. **Claim идёт строго ДО `allocate_task_seq`** — тот держит row-lock проекта до конца транзакции, обратный порядок даёт ABBA-дедлок.

**Копия не идёт через `create_task_record`** — в нём три гейта, которые на штатных данных уронили бы само закрытие задачи: `assert_project_accepts_tasks` (409 в архивном проекте, где правка задач разрешена сознательно), `assert_assignees_in_tenant` (404, если исполнителя уволили в auth) и правила личного пространства/creator-watcher от `principal`. Переиспользуются ровно `allocate_task_seq` и `next_position`; уволенные исполнители выпадают фильтром `deleted_at IS NULL`, архив задачи или проекта = мягкая остановка серии с записью `recurrence_stopped` в ленту.

**Даты — от ЯКОРЯ серии.** `services/recurrence_dates.py` считает k-й шаг от `anchor` (день срока в момент установки правила), а не от предыдущей даты: иначе «каждый месяц» от 31 января навсегда сползает на 28-е (31.01 → 28.02 → **31.03**, а не 28.03). Следующий шаг всегда строго позже сегодня, догон ограничен. Смена правила пере-якоривает серию. `next_due` считает сервер и отдаёт в `TaskResponse.recurrence` — второй реализации арифметики на клиенте нет.

**Копируется** описание, исполнители, метки, приоритет, колонка, кастом-поля и подзадачи (все невыполненными, со своими `seq`). **Не копируется**: комментарии, вложения (блоб один — `purge_blobs` при удалении любой из задач унёс бы файл у живой), зависимости (копия оказалась бы заблокирована выполненной задачей), наблюдатели `manual`/`mentioned` (подписка на конкретную задачу, а не на бесконечную серию).

**Права.** Ставит и снимает повтор редактор (`PUT`/`DELETE /api/tasks/{id}/recurrence` — отдельные ручки, потому что на `TaskUpdate` стоит `extra="forbid"`, а сама ручка расширяет права до исполнителя-viewer для `done`/`stage_id`). Порождает копию любой, кто может закрыть задачу: создание санкционировано правилом редактора, копия ничего не выбирает, объём ограничен одним потомком.

**UI.** Чип «↻ каждую неделю» в строке «Срок» на десктопе и отдельная строка `PropertyRow` на мобилке (внутрь `MobileDateCell` нельзя — там невидимый `input[type=date]` на всю ячейку). Диалог — `ResponsiveDialog` с `OptionButton` (вынесен в `components/ui/`) и предпросмотром «Следующая — 21.09.2026». Признак повтора — `MetaChip` в `TaskContextLine` (и обязательно в `hasTaskContext`) и иконка рядом со сроком на карточке доски. У повторяющейся задачи тост выполнения БЕЗ «Отменить»: обратная галочка не удалит копию и не вернёт правило.

### «Мои задачи» поглотили личное пространство (16.09)

Запрос владельца: «вместо раздела "Мои задачи" открывать личный проект — переименовать его в "Мои задачи", вместо ключа `LICNOE26` давать имя пользователя, убрать лишнюю надстройку + категория "Назначенные мной"».

**Наблюдение верное, но буквально сделать нельзя.** Личный проект — КОНТЕЙНЕР, а не вид: задача из «Маркетинга», назначенная мне, физически лежит в «Маркетинге», и перенести её в личное значит отнять у проекта. У самого загруженного человека 3 личные задачи против 38 назначенных — в «проект вместо экрана» попало бы 3 строки из 41. Поэтому ход зеркальный: **экран поглотил проект**, а не наоборот.

**Что показали цифры прода.** Личное пространство не нашли: свою личную задачу за всё время завели 9 человек из 178, а 145 видели там ровно одну — задачу-инструкцию, которую Hub заводит сам. Обратная сторона того же разделения: «Мои задачи» были ПУСТЫ у 136 человек из 154 — их единственная задача личная, а личные с экрана вырезались.

**Экран.** Шесть вкладок: четыре окна дедлайнов (личные вперемешку с рабочими) + «Личные» (инбокс со строкой создания сверху и чипом «Выполненные N») + «Назначенные мной». Активная вкладка в URL (`?tab=`), смена через `replace` — «назад» занят закрытием карточки, а `TaskInlineCreate` коммитит черновик на unmount, и переключение вкладки браузерным «назад» превращало бы полуфразу в задачу. На телефоне вкладок в строку нет: шесть подписей дают ~560px при экране 390, поэтому плавающая пилюля `MobileViewControlBar`, как на странице проекта. Карточка открывается на месте, в drawer'е; гвард `?task=` (пускал только личные задачи) и хинт «только что создана» сняты одним куском — карточка тянет задачу по id и списка не ждёт.

**Контракт `/me/tasks`.** `include_personal` по умолчанию `True`, базовый предикат — `personal_projects.my_task_scope` = «назначено мне ИЛИ лежит в моём личном». Вторая ветка обязательна: снять исполнителей у личной задачи можно явным пустым списком, и на одном `assignee_exists` такая задача исчезла бы с экрана совсем. Предикат ОБЩИЙ с `_mine` в `/me/stats` — цифра «В работе» и список под ней стоят на одном экране. Ветка написана коррелированным EXISTS с явным `correlate(Task)`: прямое `Project.personal_owner_id == me` требует джойна на `projects`, а `my_daily_stmt`/`my_created_stmt` его не делают — SQLAlchemy молча добавляла бы `projects` в FROM декартовым произведением.

**`GET /me/assigned-by-me`** — всё, что я создал и назначил другому, по всем проектам (на проде 37 задач против 2 у прежней секции «Я поставил»). Видимость — `personal_list_scope`: членство в проекте плюс правило чужого личного. Членство обязательно, иначе в списке появляются строки, которые 404-ят при клике (`/me/tasks` этим болеет и сегодня); ветки hub-admin в предикате нет сознательно — `personal_task_scope` с 15.09 админа не пропускает. Копии повторов НЕ исключаем, хотя соседний `my_created_stmt` их режет: там это «завёл руками за период», здесь фильтр спрятал бы единственную живую строку серии. `/me/delegated` живёт как deprecated до протухания PWA-бандлов.

**Имя и ключ.** Все личные проекты названы «Мои задачи»; чужому личному имя подменяется на «Личное · Имя» (`personal_display_name`) — гость иначе читает «Мои задачи» как свои. Ключ собирается из ОБОИХ слов ФИО (`personal_key_base`): первое слово не годится, потому что порядок слов в справочнике смешанный (139 против 70), и выходит `ANASTASIY`…`ANASTASIY7` — тот же `LICNOE26` в профиль. Замер на 178 владельцах: оба слова дают 171 уникальный ключ, цифровой суффикс достаётся 7 (полные тёзки). Потолок базы — **13**, а не 16: `_TASK_KEY_RE` ассистента матчит «KEY-42» целиком, а суффикс клеится после среза. Разделители вычищаются ДО `_candidate`, иначе «Блохина 1/75» уходит в ветку инициалов и даёт ключ «B». Ключ выдаётся ОДИН раз: пересчёт при переименовании человека в auth — это UPDATE под UNIQUE внутри воркера фида, чья ошибка заморозила бы фид тенанта. Существующим 179 проектам имя и ключи перевыдала `app/jobs/rename_personal_projects.py` (dry-run, аудит с `actor_id=None`, flush на каждый проект против гонки с живым `GET /api/me`).

**Ассистент.** `resolve_project` получил закрытый список синонимов («личное», «мои задачи», …): после переименования фраза «добавь мне личную задачу» не нашла бы проект ни точным совпадением, ни `ilike`, хотя `visible_projects_stmt` держит свой личный видимым именно ради неё.

**Приватность подтянута до заявленной.** Пять ручек чужого личного проекта скоуп не применяли: метки, колонки со счётчиками, определения кастом-полей, значения полей ВСЕХ задач и состав участников. Теперь первые три отдаются гостю пустыми (их зовёт карточка задачи, и 403 дал бы там тост вместо тихой деградации), последние две — 403 через `assert_full_project_access`.

**Страница личного проекта** (`/projects/{мой личный}`) редиректит на `/my?tab=personal` с сохранением `?task=` — по таким адресам ведут пуши и «Входящие». Сравнение идёт с `me.personal_project_id`, а НЕ с `project.is_personal`: флаг истинен и для ЧУЖОГО личного, куда ходит автор поручения. Доски, участников, «Поделиться» и импорта CSV у личного пространства больше нет — по прямой ссылке они были доступны, хотя гейтились только архивация и удаление.

### Поручение задачи в чужое личное пространство (15.09)

Запрос владельца: «создавать задачу прямо в личные задачи исполнителю, чтобы её видел только исполнитель и автор, но автор не видел другие личные задачи исполнителя».

**Приватность не изобреталась заново.** Она уже была построена под этот сценарий и работала «сверху вниз» (владелец сам заводит задачу и зовёт коллегу): `personal_task_scope` показывает НЕвладельцу только задачи, где он исполнитель ИЛИ наблюдатель. Автор поручения становится наблюдателем при создании (`create_task_record(watch_creator=True)`), поэтому видит ровно свою задачу и ни одной чужой. На проде под этим предикатом уже жили 7 приглашённых.

**Блокер был ровно один:** `POST /projects/{id}/tasks` стоит на `require_project_role(owner|editor)`, и посторонний в чужом личном получал 404 (существование скрыто). Ослаблять общий гейт нельзя — он же охраняет обычные проекты, поэтому появилась узкая ручка `POST /api/me/delegate` по образцу `POST /api/feedback`:

1. `get_personal_project_id(получатель)` — нет проекта (человек ни разу не заходил в Hub, таких 53 из 227) → **409** с объяснением. Заводить личное пространство за человека не стали: задача-инструкция привязана к моменту создания проекта, и он остался бы без неё навсегда;
2. `create_task_record` — задача без колонки (личное — список дел, а не доска), автор становится наблюдателем;
3. `ensure_project_member(role="viewer")` автору — без членства карточка, комментарии и вложения ответили бы 404;
4. `set_task_assignees([получатель])` + `apply_assignee_side_effects(notify=True)` отдельным шагом: внутри `create_task_record` побочки исполнителя намеренно молчат, и получатель не узнал бы о поручении.

**Поручать может любой сотрудник** (решение владельца) — защита от мусора в чужом inbox'е сводится к rate-limit `task:write` и к тому, что автор виден в задаче.

**Автор правит и удаляет ТОЛЬКО свою поручённую задачу** — `personal_projects.may_edit_delegated` («проект личный, я не владелец, но я `created_by` этой задачи»), и правило стоит в ручках `update_task`/`delete_task`, а не в общем `require_task_access`: тот охраняет приватность личного пространства целиком. Без правила получался тупик: с viewer-членством автор не мог ни исправить опечатку, ни отозвать задачу.

**Счётчики чужого личного гостю не отдаются.** `GET /projects/{id}` считал `task_count`/`done_count` по ВСЕМ задачам проекта, и членство открывало автору «37 задач, 12 закрыто» про чужие заметки — формально не задачи, но ровно та информация, которой он знать не должен. Теперь при непустом `personal_task_scope` счётчики отдаются как `None` (клиент различает `undefined` и `0`) — включая hub-admin, который с 15.09 правила личного пространства не обходит.

**Автор находит поручённое в секции «Я поставил»** (`GET /api/me/delegated`: `created_by = я`, проект личный и не мой, не выполнено, не в архиве). Иначе он свою же задачу не нашёл бы: `personal_visible_to` — это «не личный ИЛИ **мой** личный», и он стоит в поиске, в комментариях и в инструментах ассистента; трогать его нельзя, он же защищает от выгребания чужих заметок во внешнюю LLM.

**Что принято как есть:** получатель может унести поручение в рабочий проект (`assert_movable` запрещает только ЧУЖОЕ личное, своё переносится в обе стороны) — тогда задача уходит из «Я поставил», а автора-наблюдателя `_plan_watchers` может отписать, если он не участник цели. Это не поломка: задача перестала быть личным поручением.

### Задача в личном принадлежит исполнителю (15.09)

Продолжение того же разговора: «если задачу назначили лично мне — я должен видеть её в СВОЁМ личном проекте, а не в её, ибо я исполнитель». До этого назначенный коллега оставался гостем в чужом личном: задача жила у автора, а исполнитель видел её только в кросс-проектном списке и на странице чужого «Личного».

**Правило одно и живёт в одном месте** — `services/personal_handoff.py::apply_personal_assignee_rules`, вызов после КАЖДОГО изменения состава исполнителей (`create_task`, `PATCH assignee_ids`, `POST/DELETE /tasks/{id}/assignees`). Для обычных проектов не делает ничего.

1. **Исполнитель в личном ровно один** — двоих в личное не положить физически, попытка → 409 с объяснением («поручите кому-то одному или перенесите в рабочий проект»). Практическое следствие: чтобы отдать СВОЮ личную задачу, себя из исполнителей надо убрать — в личном создатель назначается автоматически, и «добавить коллегу» упирается в эту же 409.
2. **Назначил другого — задача уезжает в его личное.** Полноценным `plan_move`/`apply_move`, а не сменой `project_id`: номер перевыдаётся, позиция считается в цели, метки и кастом-поля пересобираются по одноимённым, публичная ссылка задачи отзывается. Автор остаётся наблюдателем (`_plan_watchers` не отписывает того, кто переносит) и получает viewer-членство в цели ЯВНЫМ шагом — без него он потерял бы собственную задачу из виду (`personal_task_scope` пускает наблюдателя, но карточка требует членства). Задача попадает в его «Я поставил» без отдельной ветки: условие секции — `created_by = я` в чужом личном.
3. **Подзадачу поручить нельзя** — семья переезжает целиком (`assert_movable`), поэтому отвечаем прямым 409, а не роняем ошибку из недр переноса.
4. **У получателя нет личного пространства** (ни разу не заходил в Hub) → 409, тот же текст, что у `POST /me/delegate`.

Послабление в переносе — точечное: `assert_movable(..., handoff=True)` пропускает ЧУЖОЕ личное **только как цель**. Источник обязан остаться своим личным, иначе переносом можно было бы вытащить чужую заметку. Правило симметрично: получатель, назначив задачу обратно, отправляет её назад.

**Легаси разобрала разовая джоба** `app/jobs/handoff_personal_tasks.py` (`--apply`). Переносит только однозначное: не выполнено, не в архиве, ровно один исполнитель и он не владелец, не подзадача, автор = владелец личного (иначе актором переноса быть некому), у исполнителя есть личное пространство. Всё остальное — в отчёт поимённо и не трогается. На проде под условия попали 2 задачи (LICNOE20-2, LICNOE26-5); ещё 2 выполненные остались на месте — история не переписывается, и приватность для них держат прежние предикаты (тесты на легаси-состояние собирают его мимо ручек: через API такую строку больше не создать).

### Упоминания через «@» (14.09)

Запрос сотрудника: «невозможно написать через @ имя и фамилию, Хаб не находит человека в справочнике; чтобы написать адресно, приходится заходить в почту, смотреть название учётной записи и уже её вводить через @».

**Причин было три, и каждая ломала путь сама по себе.**

1. *Клиент.* Сегмент после «@» считался по классу `[A-Za-z0-9._-]`, поэтому первая же русская буква давала `null`, попап закрывался и запрос на сервер не уходил вовсе. Прогон прежней функции в браузере: `@i` → запрос `i`, `@И` → ничего.
2. *Сервер.* Поиск шёл одной подстрокой `lower(full_name) LIKE '%запрос%'`. На живых данных из 225 двухсловных ФИО обратный порядок слов находил **0** — при том что порядок в справочнике смешанный: у 139 человек фамилия вторым словом, у 70 первым.
3. *Формат.* Личностью в упоминании был local-part почты. Из 227 живых адресов 140 содержат цифры, 108 короче девяти символов, 122 — личные ящики на gmail/yandex/mail.ru. Угадать нельзя — отсюда и поход в почту.

**Грамматика токена.** `@` и дальше буквы любого алфавита, цифры, `_`, `.`, `-`. Две формы, обе легальны и обе резолвятся: `@Иван_Петров` (ФИО, пробелы заменены подчёркиваниями) и `@petr.popov` (логин). Вторая оставлена навсегда — так написаны все прежние комментарии и так шлют застрявшие PWA-бандлы. Регулярка живёт в ТРЁХ местах и меняется только тройкой: `app/services/mention_parser.py`, `app/services/public_token.py` (там граница перед «@» сознательно не проверяется — на публичной странице маскируются и почты из текста), `web/src/lib/mentions.ts`.

**Какой токен вставить, решает сервер.** `/api/tenant/members` отдаёт готовое поле `mention`, клиент вставляет его дословно. Имя выдаётся, только если ФИО непустое, состоит из букв/цифр с разделителями ` .-` и **уникально в тенанте** (оконная функция считает тёзок по всему справочнику, а не по текущей выдаче). На проде это 218 человек из 227; остальным достаётся логин — две пары полных тёзок, один человек со «/» в имени, пара ФИО с точкой на конце. Клиент это решение не принимает: тёзки должны разбираться в одном месте.

**Неоднозначный токен-имя не резолвится ни в кого.** Попасть в текст он может только ручным набором, а уведомить — и, с этой же правки, впустить в проект — не того человека хуже, чем промолчать. Хвостовые `.` и `-` перед сравнением срезаются: «позовите @Иван_Петров.» иначе не резолвился бы, потому что точка нужна внутри логинов.

**Поиск — общий на весь продукт** (`app/services/people_search.py`): запрос режется на слова (до четырёх), каждое обязано найтись в ФИО **или** в почте, между словами AND; `ё → е` с обеих сторон (5 человек с «ё» на проде); ранжирование — сначала совпадение с начала слова, потом вхождение, потом алфавит. Потребителей двое: `/api/tenant/members` (упоминания, исполнители, наблюдатели, фильтры) и `/api/learn/employees` (экран «Сотрудники») — там ранжирование НЕ применяется, потому что экран читает список страницами и порядок обязан быть устойчивым. Индексов под `replace(lower(...))` нет сознательно: 227 теней и 305 карточек.

**Упоминание выдаёт viewer-членство в проекте** (`app/api/comments.py::_subscribe_mentioned` → `ensure_project_member`) — зеркало ручки наблюдателей: подписка без доступа вела бы в 404, а упомянуть теперь можно любого сотрудника по имени, не зная логина. Членство идемпотентно и **не отзывается**, если упоминание убрали из текста (так же, как у наблюдателей и исполнителей). В личном проекте это безопасно: `personal_task_scope` покажет приглашённому только ту задачу, где он исполнитель или наблюдатель. Следствие, принятое владельцем: упоминать может любой, кто видит задачу, включая viewer'а, — то есть viewer может привести в проект постороннего.

**Имена в отправленных комментариях.** `CommentResponse.mention_names` (токен → текущее ФИО) считает сервер ОДНИМ батчем на весь список. Раньше словарь строил клиент из `/tenant/members` с лимитом 10, и имя вместо логина видели только первые десять сотрудников по алфавиту. Имя берётся текущее — переименование в auth доезжает до старых комментариев само. Тот же словарь идёт в текст пуша (`render_mentions`), иначе в уведомлении стояло бы «@Иван_Петров».

**UI.** Попап открывается на «@» и держится через ОДИН пробел, чтобы искать «Иван Петров», а не только первое слово; два пробела, перевод строки и второй «@» сегмент обрывают, пробел сразу после «@» не считается («Стоимость 5 @ 10 руб»), длина сегмента ограничена 40 символами — иначе попап живёт до конца абзаца и перехватывает Enter. Пустая выдача показывается явно («Никого не нашли» / «Ищем…»): прежде попап просто исчезал, и это читалось как «справочник не работает». Ниже `lg` попап встаёт НАД полем — композер прижат к низу листа, и выпадашка под ним ушла бы за клавиатуру. Разбор ввода — в чистом `web/src/lib/mentions.ts` с тестами: vitest в проекте без jsdom, компонент не покрыть.

### Видео во вложениях задач (15.09)

Запрос сотрудника: приложил к задаче запись с телефона — не принялось. Текст отказа («Файл … не поддерживается») печатал КЛИЕНТ, до запроса, и это была лишь первая из пяти преград.

**Пять рубежей, и снимать их надо всеми пятью сразу.** Список расширений клиента (`attachmentTypes.ts`), клиентский потолок 20 МБ, серверный `ALLOWED_MIME`, серверный `attachment_max_bytes`, `client_max_body_size 25M` в nginx. Замер на проде 15.09: POST 30 МБ на `/api/tasks/{id}/attachments` отдаёт **413 после 65 КБ отправленного** — nginx режет по `Content-Length`, до приложения тело не доходит; тот же файл на `/api/learn/media` отдаёт 401, не 413. Был и шестой рубеж, который проявился бы после снятия первых пяти: посмотреть видео всё равно нельзя — скачивание тянуло файл блобом в память вкладки, а `<video>` не шлёт `Authorization`.

**Форматы — mp4, mov, webm** (решение владельца). Покрывают то, чем снимают: Android и запись экрана дают mp4, iPhone — mov, браузерная запись — webm. Играется не всё и не везде (Chrome не декодирует mov), поэтому у плеера есть `onError` с фолбэком на скачивание: чёрный прямоугольник без объяснения хуже честной строки. AVI и MKV не приняты сознательно — в браузере они не играются ни в одном.

**Потолок — 1 ГБ и он per-kind.** `attachments.py::attachment_size_limit(mime)`; зеркало — `attachmentTypes.ts::attachmentSizeLimit`. Клиент определяет вид по РАСШИРЕНИЮ, а не по `file.type`: браузер часто отдаёт пустую строку или `octet-stream`, и опора на MIME применила бы к видео лимит документа, не пустив до сервера файл, который сервер как раз принимает. `store_upload` принимает `max_bytes` ПАРАМЕТРОМ — его же зовёт форма обратной связи, и гигабайт не должен протечь туда молча.

**`_EXT_FALLBACK_MIME` знает три новых расширения** — без этого правка чинила бы задачу наполовину: файловые менеджеры Android и часть десктопных браузеров шлют видео как `application/octet-stream`, ровно как когда-то `.heic`. Восстанавливать эти три МОЖНО потому, что следом идёт `sniff_mismatch`, а у них есть однозначная сигнатура (ISO-BMFF `ftyp` у mp4/mov, EBML у webm). У `.svg` сигнатуры нет — он в карте отсутствует намеренно, и тест это фиксирует.

**Faststart НЕ требуем**, в отличие от медиа уроков (там 422 с инструкцией пересохранить). Камера Android пишет `moov` в конец файла, и требование вернуло бы исходную жалобу. Цена — на iOS такое видео начнёт играть не сразу; размен осознанный.

**Гейт свободного места — в ручке, не в сервисе.** У вложений его не было вовсе (стоял только у медиа уроков и бейджей). К моменту вызова ручки FastAPI уже разобрал multipart, а Starlette положила файловую часть в `SpooledTemporaryFile` (спул сверх 1 МБ уходит на диск; на проде `/tmp` — не tmpfs, лежит на корневом разделе, `PrivateTmp=no`). То есть `check_free_space()` уже видит место, съеденное спулом, и запас нужен ровно на ОДНУ копию: `media_min_free_bytes + file.size`. Неизвестный `size` трактуется как потолок вида файла, а не как ноль: гейт, который при неизвестном размере превращается в «места хватит», хуже отсутствующего — он выглядит рабочим.

**Запись чанка — через `asyncio.to_thread`.** Гигабайт это 16 тысяч синхронных `write()`; когда page cache упрётся в writeback, каждый встанет на десятки миллисекунд, а прод крутится на ОДНОМ uvicorn-воркере. Starlette по той же причине пишет свой спул через threadpool.

**Загрузка переехала на фиксированный адрес `POST /api/attachments`** (`task_id` — полем формы), старая ручка оставлена для вчерашних бандлов. Причина не в красоте URL: потолок тела задаёт nginx-локация, а сделать её под `/api/tasks/{uuid}/attachments` нельзя — путь живёт под `location ^~ /api/`, а модификатор `^~` **отменяет проверку regex-локаций**: блок `location ~ ^/api/tasks/…` прошёл бы `nginx -t` и не сработал никогда. Поднимать потолок всему `^~ /api/tasks/` значит разрешить гигабайтное тело в `PATCH /tasks/{id}`. Тем же приёмом и по той же причине сделан `location = /api/learn/media`.

**Показ — `GET /api/attachments/{id}/file?e&s`**, подпись `issue_token("attach:{id}")` (префикс отделяет пространство: подпись одного вложения не открывает другое и не годится для медиа уроков), сессия `tenant_scoped_session(None, bypass_rls=True)` — без JWT tenant-контекста нет. Права проверяются на ВЫДАЧЕ адреса: `preview_url` попадает только в ответ списка вложений, а тот стоит за `require_task_access`. Отдача — `X-Accel-Redirect: /_protected_media/{storage_key}`; **nginx под это менять не пришлось** — локация уже алиасит весь `attachments_root`, а вложения задач лежат в нём же. Проверено снаружи на проде: `Range: bytes=1500000-1500999` → `206` с корректным `Content-Range`, битая подпись → `403`.

**Часовая сетка `issue_token` здесь несущая, а не декоративная.** Глобальные дефолты клиента — `staleTime: 30_000` и `refetchOnWindowFocus: true`, то есть список вложений перезапрашивается при каждом возврате на вкладку. Без округления `exp` `src` у `<video>` менялся бы на каждый рефетч, элемент перезагружался, позиция сбрасывалась — тот самый баг, который ловили на staging 25.08 на уроках.

**`dl=1` переключает `Content-Disposition` на attachment.** Та же ссылка, но «сохранить»: скачивание гигабайта обязано идти мимо JS, а показ в `<video>` требует именно inline. `preview_url` заполняется **только у `video/*`** — inline-превью картинок это отдельная задача, и HEIC/HEIF из неё придётся исключать.

**Своя зона лимита при отдаче.** `location ^~ /api/attachments/` берёт `hub_media` (60 r/s, заведена «под Range-бёрсты видео»): перемотка это серия Range-запросов, и в общей `hub_api` (30 r/s) она ловит 429 посреди просмотра. Локация накрывает ТРИ ручки — отдачу, старое `/download` и `DELETE`, — поэтому набор `proxy_set_header` в ней обязан быть полным.

**Плеер.** `preload="metadata"` (не `auto`: гигабайт начал бы выкачиваться при открытии карточки), `playsinline` (иначе iOS уводит воспроизведение в системный полноэкранный плеер), `onError` с фолбэком. Прогресс загрузки обязателен: гигабайт по мобильному каналу идёт десятки минут, и без индикатора это неотличимо от зависшего приложения; клиентского таймаута нет — `axios.create` в проекте вызван без `timeout`.

**Побочная находка, исправленная заодно.** У формы обратной связи `TOTAL_BYTES_MAX` был 50 МБ — БОЛЬШЕ, чем принимает nginx (`client_max_body_size 25M`): набор на 30 МБ проходил все четыре клиентские проверки и получал голый 413. Выровнено до 24 МБ в паре `feedback.py` ↔ `feedbackFiles.ts`. Видео в форме осталось разрешённым (короткая запись экрана в баг-репорте полезна), но на 20 МБ — у формы свой `FILE_BYTES_MAX`.

### Инварианты по доменам (полный список, hot-выжимка — в CLAUDE.md)

- **FK-инвариант:** «действует человек (actor/author/owner) → `shadow_users.employee_id`; данные О человеке (прогресс, назначения, ознакомления, членства) → `employee_profiles.id`». `employee_profiles.employee_id` NULL до первого входа; матчинг по `lower(email)` в `/api/me` — ТОЛЬКО для principals с hub-ролью.
- **Личность сотрудника принадлежит auth (28.08), профиль её зеркалит.** У человека в Hub два хранилища имени: `shadow_users.full_name` (зеркало JWT, апсертится в `deps.py::get_db` на КАЖДОМ запросе — его читает весь трекер: пикер участников, исполнители, наблюдатели, комментарии, лента) и `employee_profiles.full_name` (его читает всё «Обучение»: списки, аудитории, отчёты, тексты уведомлений). Пока второе правилось руками на экране «Управление → Сотрудники», имена расходились — переименование в auth до learn не доезжало (на проде 3 расхождения из 18, включая «Дудин Никита» против «Никита Дудин»: не сбой синхронизации, а два несогласованных формата). Решение владельца: имя одно, источник — auth.
  - **Синхронизация** — `app/services/employee_profiles.py::_sync_linked_profile`, рядом с веткой email: непустое `principal.full_name`, отличающееся от профиля, перезаписывает его и пишет `audit.record(action="update", object_type="employee_profile", diff={"full_name": …})`. Пустое имя в токене профиль НЕ трогает: в списках это единственный опознавательный признак человека. Лишнего запроса не появилось — UPDATE там и так выполнялся ради `last_activity_at`.
  - **Гейт правки** — `app/api/employees.py::update_employee`: при `last_activity_at IS NOT NULL` отличающиеся `full_name`/`email` дают 422 с текстом «меняется в его профиле в auth». Три решения, каждое из которых обязательно: критерий — `last_activity_at`, а НЕ наличие `employee_id` (ручки `/link` и `/restore` проставляют id без входа человека, и карточка, привязанная вручную, замёрзла бы с HR-опечаткой, которую уже не исправить); сравнение — со значением, а не с присутствием ключа (форма шлёт весь объект, поэтому «поле пришло → 422» ломало бы сохранение должности, магазина и роли, а заодно вчерашние PWA-бандлы); email закрыт тем же гейтом не за компанию — `_sync_linked_profile` перетирает его из auth с самого начала, то есть поле в редакторе врало ровно так же.
  - **Фронт** — `LearnEmployeesPage.tsx`: `authOwnsIdentity = !isNew && profile.last_activity_at !== null` гасит «ФИО» и «Email» и исключает их из payload; подсказки под полями нет сознательно (решение владельца: недоступное поле объясняет себя само). Создание карточки и правка не заходившего имя принимают — HR заводит человека до появления аккаунта.
  - **Переименование доезжает без входа человека (28.08).** По запросу Hub auth завёл в продуктовом фиде `GET /api/products/deletions` событие `employee_updated` с новым ФИО в теле; писать его в фид, а не отдавать lookup-ручкой, решили ради самодостаточности события. Ключевое, что легко упустить: `fetch_deletions` собирает событие по ФИКСИРОВАННОМУ списку ключей, поэтому без релиза клиентской библиотеки поле молча не доехало бы — нужен `signaris-auth-client>=0.8.0` (пин в `pyproject.toml`). Библиотека сама обновляет `shadow_users.full_name` (`rename_shadow_user`) после `on_event`; вторую копию имени пишет `app/services/deletion_sync.py::_apply_rename` — своя `tenant_scoped_session` (сессия воркера предназначена только для очереди и зеркала, `employee_profiles` под RLS), только UPDATE существующей карточки (фид не должен становиться каналом создания записей о людях), guard на пустое имя, выход при совпадении и аудит с `actor_id=None`. Ошибку БД ветка НЕ глушит: курсор двигается после обработчика, значит событие переиграется — молчаливая потеря переименования хуже повтора. Событие несёт ПДн, поэтому имя не логируется, а на движке выставлен `hide_parameters=True` (`app/db.py`): текст SQLAlchemy-ошибки рендерит параметры запроса. Тесты — `tests/integration/test_deletion_sync_rename.py` (до 28.08 у deletion-sync не было ни одного). **Курсор при подключении нового типа событий нужно откатывать вручную**: старый бандл прожёвывает неизвестный тип как no-op и двигает курсор, события сами не переигрываются (`UPDATE sync_state SET cursor = … WHERE key = 'deletion_sync'`, ключ именно такой, строку НЕ удалять — `_load_cursor` вставит 0 и переиграет фид с начала, включая архивацию профилей по старым `employee_deleted`; сервис на время правки остановить, иначе `_save_cursor` перезапишет). На staging фид выключен флагом `SIGNARIS_HUB_DELETION_SYNC_ENABLED=false`.
  - **Разовой джобы выравнивания нет и не будет.** Она копировала бы `shadow_users → employee_profiles`, но shadow сам обновляется только при заходе: у `hr@uppetit.ru` профиль уже верный («HR Пользователь»), а зеркало протухло («Скробот Мария») — джоба откатила бы имя назад. Расхождения сходят на нет по мере входов, наблюдать — `select p.email, p.full_name, s.full_name from employee_profiles p join shadow_users s using (employee_id) where p.full_name is distinct from s.full_name`.
  - **Следствия, принятые владельцем:** трекер показывает новое имя сразу, «Обучение» — со следующего старта приложения (профиль синхронизируется в `/api/me`, а не на каждом запросе); формат имён станет auth-овским; сортировка списка сотрудников (`employees.py`, по `EmployeeProfile.full_name`) поедет вслед за видимым именем; имя в текстах learn-уведомлений сменится — это и есть цель. Снапшоты выданных сертификатов не трогаются: там историческая запись. Тесты — `tests/integration/test_profile_identity.py`.
- **Audience-движок:** контентный объект несёт `audience_id NULL`(=всем) → правила в `audience_rules` (include: AND непустых измерений внутри строки, OR между строками; exclude вычитается; пустая include-строка запрещена) → материализация в `audience_members` (granted_at!). Фильтр списков — `visible_filter()` из `app/services/audience_resolver.py`. Пересчёты — под per-tenant advisory-lock, diff/upsert (granted_at сохраняется). Атрибуты ТУ расширяются закреплёнными магазинами, франчайзи-владельца — его магазинами; франчайзи рядового — из store.franchisee_id. Измерения: 9 uuid[]-справочников + скалярный «контур» `org_roles` (employee|tu|franchisee_owner|office, 0031). - **«Скрыто ото всех» — `audiences.is_none` (0051):** третье явное состояние аудитории (кнопка в `AudiencePicker`, ОС 01.09 — запущенную аттестацию прятали, исключая 261 сотрудника по одному). Оверлей: строки правил СОХРАНЯЮТСЯ (снятие флага возвращает прежнюю аудиторию без перенастройки), а пересчёт вычищает `audience_members` в ноль — поэтому все потребители видимости (visible_filter, обходные «audience_id IS NULL ⇒ всем» в аттестациях/квизах, поиск, RAG) гаснут без правок. Флаг обязан доезжать до КАЖДОГО вызова `audience_matches` (их три, все в resolver'е) — иначе nightly rebuild пере-добавит членов; ветка `is_none` в `set_object_audience` идёт ДО ветки «всем-удалить», обычное сохранение флаг сбрасывает. ### Роли learn-домена

Осей четыре и они независимы: JWT `hub:admin|member|viewer`, роль в проекте
(`project_members.role`), `content_role` (none|author|publisher) и `org_role`
(employee|tu|franchisee_owner|office). **Полный разбор — `docs/ROLES.md`:** что

### Тема принадлежит учётной записи (0054, 09.09)

ОС владельца: на общем устройстве A выбрал светлую тему, вышел, вошёл B — и получил тему A. Тема жила только в `localStorage['hub-theme']`, то есть была настройкой браузера.

**Хранение.** `user_preferences` (PK `employee_id` → FK `shadow_users.employee_id` ON DELETE CASCADE, `tenant_id`, `theme VARCHAR(8) NULL` + CHECK, `updated_at`; RLS + FORCE). Форма скопирована с `notification_preferences`. Почему не иначе: `shadow_users` — зеркало auth, его перестраивает staff-sync; `employee_profiles` не существует у principal без hub-роли и у архивных карточек (повторный найм), а тему видит каждый, кто видит экран. **`theme` NULLABLE и без DEFAULT** — «строка есть, выбор не сделан» ≠ «выбрал тёмную»; на различии стоит посев.

**API.** Чтение — поле `theme` в `GET /api/me` (`app/api/me.py`), запись — `PUT /api/me/preferences` (`require_auth_any`, тело `{theme}` с `extra="forbid"`, upsert `on_conflict_do_update`). Отдельной GET-ручки нет: второй источник = второй способ разъехаться. Сборка SQL отделена от исполнения (`app/services/user_prefs.py`) ради юнит-теста на компиляцию — интеграционные тесты в CI не бегут.

**Контракт из трёх состояний** (`web/src/hooks/useMe.ts::Me.theme`, решение — `web/src/lib/themeSync.ts::decideThemeSync`):

| Значение | Смысл | Что делает фронт |
|---|---|---|
| поля нет (`undefined`) | старый бэкенд в окне деплоя, dev-стенд с фикстурой | синхронизации нет, тумблер работает локально |
| `null` | запись/выбора нет | ОДИН раз засевает локальный выбор (`seed`) |
| `'light'`/`'dark'` | сервер решил | применяет и перезаписывает кеш (`adopt`) |

Слить `undefined` и `null` нельзя: `dev/tracker.tsx` монтирует настоящий `Shell` с фикстурой без `theme`, и стенд начал бы слать PUT в несуществующий бэкенд.

**Порядок покраски:** инлайн-скрипт `web/index.html` (до первой отрисовки, кеш) → `initTheme()` на старте бандла → `useThemeSync` в `Shell` после ответа `/me` (сервер) → `storage`-событие в соседних вкладках. Кеш нужен для холодного старта PWA без сети, поэтому не удаляется, а понижается в статусе. Тег `hub-theme-owner` помечает, чей кеш: посев НЕ переносит чужой выбор в аккаунт (иначе исходный баг переехал бы в БД).

**Инварианты.** Писать тему только через `setThemeLocal` (он идёт через стор: от `useTheme` зависят бренд-ассеты сайдбаров и тема тостов, покраска одного `data-theme` даёт светлую тему с тёмным логотипом). Различать «ключа нет» и «дефолт» только через `readStoredRaw`. Мутация обязана делать `cancelQueries(['me'])` + оптимистичный `setQueryData`, а `meQueryOptions` — передавать `signal` (без него отменённый рефетч доживает и перетирает свежий выбор). Тело инлайн-скрипта и имя ключа `hub-theme` неприкосновенны — CSP-хеш в трёх nginx-конфигах, которые деплой не возит.

**Выход из аккаунта** — `web/src/lib/session.ts::logoutWithDeviceCleanup`, единственная точка (четыре кнопки зовут её). Отзывает push-привязку на сервере, чистит следы человека по явному списку `lib/deviceState.ts` и уходит на SSO-логаут. Список явный, а не `localStorage.clear()`: тот снёс бы `sso_pkce_verifier`/`sso_return_path` (сломав вход) и гард `hub:preload-reload-at`.

## Безопасность

- JWT claims читаются **только** через `signaris-auth-client` — никакого ручного `jwt.decode`.
- CORS на backend разрешает только `https://hub.signaris.ru` и `https://hub-staging.signaris.ru`.
- Rate-limit через Redis (с DB-fallback): паттерн скопирован из `CentralAuthService/app/security/rate_limit.py`.
- Refresh-cookie общий на `.signaris.ru`. Для PWA standalone (iOS) — режим `X-Auth-Mode: api`, refresh-token в IndexedDB.

## «Гусиная гонка» (0057, 2026-09-17)

Заявка UPPETIT: соревнование точек по наполняемости чека (среднее число позиций в чеке) на данных iiko. План — `~/.claude/plans/uppetit-hazy-giraffe.md`, hot-выжимка — CLAUDE.md.

- **Данные.** Один OLAP-вызов на всю сеть за окно ≤ 14 дней: SALES, `group_by [Department.Id, OpenDate.Typed]`, `aggregate [DishAmountInt, UniqOrderId.OrdersCount]`, фильтр `DishType IN (GOODS, DISH)` (модификаторы — не позиции). Спека `RACE_SALES` и парсер `parse_daily_rows` — в `app/services/iiko/reports.py` (имена полей живут только там). Клиент гонки — `race_client()` с таймаутом 120 с. Лок слота лицензии стал fenced (`try_acquire`/`release` с Lua-CAS, TTL 300): безусловный `DELETE` снимал бы чужой лок после истечения TTL.
- **Позиция считается на чтении** (`services/race/read.py::live_rows`): накопленное с начала заезда против эффективной базы (`baselines.load_baselines`: строка `(store, race_id)` иначе `(store, NULL)`), клетки `clamp(round(100·avg/base), 0, 400)`, без базы — 100 и `needs_baseline`, места точке без базы не даются. Арифметика — `services/race/math.py` под юнит-тестами.
- **Ночное закрытие** (`engine.close_day`): снимки за все пропущенные дни (`pending_snapshot_days`), рекорд по закрытому дню (не первый день, > 100 и > прежнего максимума), при `ends_on ≤ close_day` — `finish_race` (итоги заморожены, места `math.rank`), следующий заезд через `activate_due`; базу следующего заезда в режиме `race` считает ДЖОБА после commit (`CloseReport.races_needing_baseline`) — advisory-лок берётся только вокруг записи, не поверх OLAP. **Список «кому нужна база» считается ОБЩИМ правилом по датам, а не веткой завершения** (19.09): незавершённый заезд со `starts_on ≤ close_day + 1` без строки `source='iiko'` (`baselines.has_iiko_baseline`; именно iiko — ручная база одной точки не должна отменять расчёт остальным). Одно условие покрывает смену заездов по расписанию, пробел после досрочного завершения (`force_finish` базу не считает, а в прежней ветке завершения уже завершённый заезд не появлялся — до 19.09 в режиме `race` следующий заезд после досрочного закрытия стартовал без базы) и старт «завтра» из `start_early`; ночь, когда iiko был занят, догоняется следующей.
- **Ранний старт заезда** (19.09; ТЗ §5.3 «принудительный старт», решение владельца — узкая форма): `engine.start_early` + `POST /learn/race/admin/races/{id}/start`. Кнопку получает ОДИН заезд — первый запланированный активного конкурса, когда активного заезда нет и предыдущий завершён; кандидата и день считает сервер (`math.early_start_candidate` → `RaceRefOut.early_start_on`, заполняется только в админских ответах). День атомарен: не раньше `prev.ends_on + 1` (`math.early_start_day`) — оба заезда посчитали бы одни чеки, поэтому в день досрочного закрытия кнопка предлагает «завтра». `ends_on` не двигается (даты объявлены людям, зачёт — по местам), заезд просто длиннее — в админке подпись «· N дней вместо M» считается из дат, отдельного признака и миграции нет, запись в `audit_log` (`object_type='race'`, diff `starts_on`). Режим `race`: при старте «сегодня» база считается в запросе из iiko (дата ставится ДО расчёта — `compute_baselines` берёт якорь из `race.starts_on`; лок — после OLAP, как в `force_finish`), при «завтра» — ночной джобой по общему правилу. Активация — тем же `activate_due`; пуш «заезд стартовал» уходит ближайшим тиком после 09:00 (`started_notified_at` пуст, текст берёт новые даты). Два админа одновременно: после лока `refresh(race)` и повторная проверка статуса → 409. Ранний старт ЗАПЛАНИРОВАННОГО конкурса вне объёма — пересоздание за минуту.
- **Закрытие и запуск точек (19.09, 0058).** Состав конкурса сверяется с Оргструктурой ежечасно (`engine.reconcile_participants` в `race_sync` ДО выгрузки — при занятом iiko состав всё равно обновлён) и по кнопке «Обновить из реестра»: `materialize_participants` добавляет новые привязанные точки (дедуп по подразделению как прежде), живые участники с архивной карточкой (`stores.archived_at`, в т.ч. по реестру) выводятся с `exclude_reason='closed'`, `excluded_by=NULL`, аудит `race_participant`. Возврат только руками: `manual` не переписывается, разархивированная карточка сама не возвращается. Закрытая точка уходит из общего зачёта вместе с составом (`standings` считает по `load_participants`), её замороженные итоги в завершённых заездах остаются.
