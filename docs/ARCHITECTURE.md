# Architecture

## Принципы

1. **Единая авторизация.** Никакого собственного логина — только SSO через [auth.signaris.ru](https://auth.signaris.ru) по чек-листу `CentralAuthService/client-libs/INTEGRATION.md` (13 шагов + §14 deletion-sync). Без per-product «снежинок».
2. **Multi-tenancy через RLS.** Каждая бизнес-таблица — `tenant_id UUID NOT NULL` + Postgres-policy. Приложение работает от non-superuser-роли (RLS реально enforced), миграции — от migrate-роли (BYPASSRLS).
3. **Shadow-таблицы.** `shadow_tenants` + `shadow_users` (с `deleted_at TIMESTAMPTZ NULL`) апсертятся на каждый authenticated-запрос. Доменные FK ссылаются на `shadow_users.employee_id` — не на JWT.sub.
4. **Deletion-sync.** Воркер `run_deletion_sync_worker` (lib ≥ 0.4.0) в lifespan тянет события из `auth.signaris.ru/api/products/deletions`. `on_event` — no-op (история тасков сохраняется); списки сотрудников фильтруются `WHERE shadow_users.deleted_at IS NULL`.
5. **Staff-sync (0052, «auth — источник штата»).** Pull-воркер `app/services/staff_sync.py` (15 мин + кнопка) тянет `GET /api/products/employees?product=hub` (контракт — `docs/handoffs/HUB_TASK_staff_endpoint.md`; 404 до выката auth → тихий no-op): тени + кеш `hub_role/auth_active/staff_synced_at`, карточки всем с hub-ролью ДО первого входа (`ensure_profile_for_staff_row`, без `last_activity_at`), снапшот `auth_invitations`, страховка deleted→архив. INSERT теней здесь легален — pull-bootstrap, не фид. Подробно — `docs/ROLES.md` §«Откуда Hub знает штат».

## Backend

- **FastAPI** async + lifespan: JWKS-warmup, Redis pool, фоновые воркеры deletion-sync и sid-sync (оба через `worker_supervisor.supervise` — рестарт с backoff + Redis leader-lock), Sentry init (опц.). In-memory store sid-sync блокирует `--workers > 1` (см. TECH_DEBT).
- **`tenant_scoped_session(tenant_id, *, bypass_rls)`** — async ctx manager (`app/db.py`), паттерн CentralAuthService (post-`3cfb256`). Помечает сессию `session.info["rls_scope"]`; листенер `_apply_rls_on_begin` (`after_begin`) ставит `app.tenant_id`/`app.bypass_rls` через `SET LOCAL` на старте каждой транзакции (переживает mid-request commit + смену соединения в пуле — session-level вариант дал кросс-tenant утечку 2026-08-01, см. TECH_DEBT). Для lib-воркеров с сырой фабрикой — `bypass_session_factory()`.
- **`require_auth = build_require_auth(verifier)`** — `signaris-auth-client.TokenVerifier` валидирует RS256-JWT по JWKS. Никакой собственной валидации.
- **Shadow upsert middleware** — после `require_auth`: `upsert_shadow_tenant(db, principal)` + `upsert_shadow_user(db, principal)` + commit.

## Frontend (PWA)

- **React 18 + TS strict** + Vite + `vite-plugin-pwa` (`registerType: 'prompt'`, `strategies: 'injectManifest'`).
- **Auth:** `createSsoAuthClient({...})` из `@signaris/auth-client/browser` + `attachAxiosAuth(api, authClient)`. Refresh-token — в IndexedDB (PWA standalone), access-token — в памяти через zustand.
- **Service Worker:** `web/src/sw.ts` — precache + push handler + notificationclick + SKIP_WAITING-message.
- **Update mechanism:** `UpdateBanner.tsx` проверяет SW каждые 60с + на `visibilitychange` — лечит iOS PWA-freeze таймеров в фоне.

### Задачи
- `tasks` (project_id, parent_task_id, title, description markdown, done BOOLEAN + completed_at под CHECK, priority: `low` | `medium` | `high` | `urgent`, start_at, due_at, position NUMERIC, search_vector tsvector).

Кому какая — `guides_for_role` (hub-admin: обе, остальные: сотрудницкая), ссылки приходят готовыми в `GET /api/me`. Первая задача сотрудника («Изучите инструкцию») заводится в момент создания личного проекта — `services/onboarding.py`, вызов в `ensure_personal_project`

Открыта любому сотруднику: rate-limit 5/час; с 02.09 автор ПОДПИСЫВАЕТСЯ наблюдателем и получает viewer-членство в проекте обратной связи явными шагами (`ensure_watcher(reason="creator")` + `ensure_project_member`; `watch_creator=False` остался — побочки create молчат и членства не дают); проверки файла — общий `services/attachments.py::store_upload`. Детали и причины — `app/services/feedback.py`.
- `project_stages` (project_id, name, position; 0040, свободные с 0044) — колонки доски: ТОЛЬКО имя и позиция, системного смысла нет. `tasks.stage_id` НЕОБЯЗАТЕЛЕН (0046): `NULL` = «без статуса» — задача есть в списке, календаре, поиске и `/me/tasks` (там `outerjoin`), но не на доске; новая задача без явного `stage_id` уходит в первую колонку. FK без `SET NULL`: удаление колонки с задачами требует выбора — `move_to` (перенести) или `detach` (оставить без колонки), без обоих 409. Колонок у проекта может не быть вовсе (26.08): новый проект рождается пустым, и удалить можно любую колонку, включая последнюю; состояние задачи — независимая ось `tasks.done`, пишет её только `app/services/stages.py::set_done`. - `task_activity` (append-only event log)
- `task_dependencies` (predecessor/successor, finish-to-start, BFS cycle-check `app/services/dependency_cycle.py`, миграция 0010) — стрелки на Timeline
- `custom_field_definitions` + `task_custom_field_values` (7 типов, миграция 0007) — колонки List, агрегаты Dashboard

### Перенос задачи между проектами (28.08)

`POST /tasks/{id}/move` + `GET /tasks/{id}/move-preview`, обе — `app/api/tasks.py`, работа — `app/services/task_move.py`.

**Почему отдельная ручка, а не поле в PATCH.** На `TaskUpdate` стоит `extra="forbid"` (0045) — вчерашний PWA-бандл получил бы 422 вместо no-op; `update_task` расширяет права до viewer'а для `ASSIGNEE_EDITABLE_FIELDS`, и переносу там не место; ответ PATCH по инварианту не несёт `can_complete`, а переезд обязан вернуть новый ключ.

**Почему план и исполнение — две функции.** `plan_move` считает, `apply_move` раскладывает посчитанное. Предпросмотр в диалоге и сама запись идут по ОДНОМУ коду: вторая реализация правил «что переедет» разошлась бы с первой на первой же правке. `dry_run` «сделать и откатить» (как у импорта CSV) не подошёл: `allocate_task_seq` инкрементит `projects.next_task_seq` до отката, и диалог, где человек перебирает пять целей, оставил бы дыру в каждой. `plan_move` не пишет ничего, `new_key` у предпросмотра — `null`.

**Что делает переезд.**

| | правило и причина |
|---|---|
| номер | новый, через `allocate_task_seq` цели — `uq_tasks_project_seq` иначе падает. Старый ключ уходит в ленту (`kind="moved"`, payload `from_key`/`to_key`/`from_project`/`to_project`) — это единственный его след, ссылки «PLP-118» в переписке больше не сходятся |
| семья | подзадачи едут за родителем, нумеруются по возрастанию старого `seq`. Одна подзадача — 409: `parent_task_id` — FK на `tasks.id` без проектного ограничения, БД разрыв стерпит, а `SubtaskList` ищет детей в списке нового проекта и покажет ноль |
| позиция | `next_position(db, target, stage_id=…)` каждой переехавшей. Позиция — `max+1` внутри (проект, колонка), и число из чужой шкалы поставило бы задачу в середину списка |
| колонка | у корня — из запроса (`None` = «без статуса», 0046), у подзадач — по совпадению ИМЕНИ, через `.get()` а не индекс. Оставить `stage_id` как есть нельзя: FK на `project_stages` проектом не ограничен и намеренно без `SET NULL` — строка сохранится, а на доске цели задача не появится никогда |
| метки | по точному совпадению имени; новых меток в цели не заводим — перенос задачи не должен править справочник чужого проекта |
| кастом-поля | по паре (имя, ТИП): по одному имени число уехало бы в текстовое поле. `select`/`multi_select` пересобираются по ЛЕЙБЛУ опции (id у одноимённых полей свои), финальный фильтр — `custom_field_validator.validate` |
| исполнители | `ensure_project_member(viewer)` в цели — иначе человек узнает о переносе по 403 из пуша |
| наблюдатели | не ставшие участниками — отписываются, их `notifications` по задаче удаляются. Членство в ЦЕЛИ перенос не раздаёт: доступ в целевой проект — решение его редакторов, а не побочка переноса (с 02.09 редактор может подписать человека обратно вручную — `POST /tasks/{id}/watchers` выдаёт viewer-членство явно). Исключение — САМ переносящий: права редактора в цели у него только что проверены, и без оговорки админ отписывался от собственной задачи (найдено на staging 28.08) |
| зависимости | связи со вторым концом в старом проекте удаляются: `api/dependencies.py` отвечает 400 на кросс-проектные, и переезд не должен оставлять на данных то, чего ручка не создаёт |
| уведомления | `url` переписывается на новый проект (`services/notify.py` кладёт туда `project_id` на момент отправки) |
| публичная ссылка | `scope=task` переехавших ОТЗЫВАЕТСЯ. `api/public.py::_build_task_view` проект не смотрит вовсе, поэтому переезд в личное сделал бы личное публичным в обход `assert_not_personal`. `public_share_tokens` — одна из четырёх таблиц БЕЗ RLS, `tenant_id` в условии обязателен |

**Права и запреты.** Редактор в ОБОИХ проектах (`require_task_access` + `require_project_role`), задача берётся `FOR UPDATE` (два одновременных переноса иначе выдали бы два номера и один отчёт-обманку). **Личный проект с любой стороны обязан быть своим** — иначе 409, в том числе hub-admin'у: его пропускает и `require_project_role` (админ-байпас), и `personal_task_scope` (для админа возвращает `None`). Цель архивная — 409, тот же проект — 400. Предпросмотр — свой bucket `task:move-preview` (60/мин): в общем `task:write` перебор целей в диалоге упирался бы в 429 на следующей правке задачи.

**Отчёт `TaskMoveReport`** несёт счётчики (`labels_kept`/`labels_total`, `values_*`, `watchers_dropped`, `dependencies_dropped`, `shares_revoked`, `subtasks`) и флаг `target_public` — у цели активна ссылка `scope=project`, а `_build_project_view` отдаёт анонимам ВСЕ задачи проекта, то есть приехавшая станет публичной без «явного акта над ней».

**Ассистенту инструмента переноса не дано** — по той же причине, что и `delete_task`: нужны права в двух проектах, и результат необратимо меняет номер.

**Фронт.** Строка «Проект» первой в свойствах карточки (обе раскладки), `components/task/MoveTaskDialog.tsx` на `ResponsiveDialog`, чистые `lib/taskMove.ts` (`moveTargets` — цели, `describeTaskMove` — текст по отчёту сервера). Карточка считает проект от `task.project_id`, а НЕ от пропа страницы, и после переноса уводит на `/projects/{новый}?task=`. Мутация `useMoveTask` инвалидирует десять корней кэша предикатом: переезд меняет два проекта, и перечисление ключей по одному гарантированно что-нибудь забудет. Массовая разноска по меткам осталась за одноразовой джобой `app/jobs/split_project_by_labels.py`.

### Инварианты по доменам (полный список, hot-выжимка — в CLAUDE.md)

- **FK-инвариант:** «действует человек (actor/author/owner) → `shadow_users.employee_id`; данные О человеке (прогресс, назначения, ознакомления, членства) → `employee_profiles.id`». `employee_profiles.employee_id` NULL до первого входа; матчинг по `lower(email)` в `/api/me` — ТОЛЬКО для principals с hub-ролью.
- **Личность сотрудника принадлежит auth (28.08), профиль её зеркалит.** У человека в Hub два хранилища имени: `shadow_users.full_name` (зеркало JWT, апсертится в `deps.py::get_db` на КАЖДОМ запросе — его читает весь трекер: пикер участников, исполнители, наблюдатели, комментарии, лента) и `employee_profiles.full_name` (его читает всё «Обучение»: списки, аудитории, отчёты, тексты уведомлений). Пока второе правилось руками на экране «Управление → Сотрудники», имена расходились — переименование в auth до learn не доезжало (на проде 3 расхождения из 18, включая «Дудин Никита» против «Никита Дудин»: не сбой синхронизации, а два несогласованных формата). Решение владельца: имя одно, источник — auth.
  - **Синхронизация** — `app/services/employee_profiles.py::_sync_linked_profile`, рядом с веткой email: непустое `principal.full_name`, отличающееся от профиля, перезаписывает его и пишет `audit.record(action="update", object_type="employee_profile", diff={"full_name": …})`. Пустое имя в токене профиль НЕ трогает: в списках это единственный опознавательный признак человека. Лишнего запроса не появилось — UPDATE там и так выполнялся ради `last_activity_at`.
  - **Гейт правки** — `app/api/employees.py::update_employee`: при `last_activity_at IS NOT NULL` отличающиеся `full_name`/`email` дают 422 с текстом «меняется в его профиле в auth». Три решения, каждое из которых обязательно: критерий — `last_activity_at`, а НЕ наличие `employee_id` (ручки `/link` и `/restore` проставляют id без входа человека, и карточка, привязанная вручную, замёрзла бы с HR-опечаткой, которую уже не исправить); сравнение — со значением, а не с присутствием ключа (форма шлёт весь объект, поэтому «поле пришло → 422» ломало бы сохранение должности, магазина и роли, а заодно вчерашние PWA-бандлы); email закрыт тем же гейтом не за компанию — `_sync_linked_profile` перетирает его из auth с самого начала, то есть поле в редакторе врало ровно так же.
  - **Фронт** — `LearnEmployeesPage.tsx`: `authOwnsIdentity = !isNew && profile.last_activity_at !== null` гасит «ФИО» и «Email» и исключает их из payload; подсказки под полями нет сознательно (решение владельца: недоступное поле объясняет себя само). Создание карточки и правка не заходившего имя принимают — HR заводит человека до появления аккаунта.
  - **Переименование доезжает без входа человека (28.08).** По запросу Hub auth завёл в продуктовом фиде `GET /api/products/deletions` событие `employee_updated` с новым ФИО в теле; писать его в фид, а не отдавать lookup-ручкой, решили ради самодостаточности события. Ключевое, что легко упустить: `fetch_deletions` собирает событие по ФИКСИРОВАННОМУ списку ключей, поэтому без релиза клиентской библиотеки поле молча не доехало бы — нужен `signaris-auth-client>=0.8.0` (пин в `pyproject.toml`). Библиотека сама обновляет `shadow_users.full_name` (`rename_shadow_user`) после `on_event`; вторую копию имени пишет `app/services/deletion_sync.py::_apply_rename` — своя `tenant_scoped_session` (сессия воркера предназначена только для очереди и зеркала, `employee_profiles` под RLS), только UPDATE существующей карточки (фид не должен становиться каналом создания записей о людях), guard на пустое имя, выход при совпадении и аудит с `actor_id=None`. Ошибку БД ветка НЕ глушит: курсор двигается после обработчика, значит событие переиграется — молчаливая потеря переименования хуже повтора. Событие несёт ПДн, поэтому имя не логируется, а на движке выставлен `hide_parameters=True` (`app/db.py`): текст SQLAlchemy-ошибки рендерит параметры запроса. Тесты — `tests/integration/test_deletion_sync_rename.py` (до 28.08 у deletion-sync не было ни одного). **Курсор при подключении нового типа событий нужно откатывать вручную**: старый бандл прожёвывает неизвестный тип как no-op и двигает курсор, события сами не переигрываются (`UPDATE sync_state SET cursor = … WHERE key = 'deletion_sync'`, ключ именно такой, строку НЕ удалять — `_load_cursor` вставит 0 и переиграет фид с начала, включая архивацию профилей по старым `employee_deleted`; сервис на время правки остановить, иначе `_save_cursor` перезапишет). На staging фид выключен флагом `SIGNARIS_HUB_DELETION_SYNC_ENABLED=false`.
  - **Разовой джобы выравнивания нет и не будет.** Она копировала бы `shadow_users → employee_profiles`, но shadow сам обновляется только при заходе: у `hr@uppetit.ru` профиль уже верный («HR Пользователь»), а зеркало протухло («Скробот Мария») — джоба откатила бы имя назад. Расхождения сходят на нет по мере входов, наблюдать — `select p.email, p.full_name, s.full_name from employee_profiles p join shadow_users s using (employee_id) where p.full_name is distinct from s.full_name`.
  - **Следствия, принятые владельцем:** трекер показывает новое имя сразу, «Обучение» — со следующего старта приложения (профиль синхронизируется в `/api/me`, а не на каждом запросе); формат имён станет auth-овским; сортировка списка сотрудников (`employees.py`, по `EmployeeProfile.full_name`) поедет вслед за видимым именем; имя в текстах learn-уведомлений сменится — это и есть цель. Снапшоты выданных сертификатов не трогаются: там историческая запись. Тесты — `tests/integration/test_profile_identity.py`.
- **Audience-движок:** контентный объект несёт `audience_id NULL`(=всем) → правила в `audience_rules` (include: AND непустых измерений внутри строки, OR между строками; exclude вычитается; пустая include-строка запрещена) → материализация в `audience_members` (granted_at!). Фильтр списков — `visible_filter()` из `app/services/audience_resolver.py`. Пересчёты — под per-tenant advisory-lock, diff/upsert (granted_at сохраняется). Атрибуты ТУ расширяются закреплёнными магазинами, франчайзи-владельца — его магазинами; франчайзи рядового — из store.franchisee_id. Измерения: 9 uuid[]-справочников + скалярный «контур» `org_roles` (employee|tu|franchisee_owner|office, 0031). Правила перечитываются: `GET /learn/audiences/{id}` (+`profile_labels`) → посев диалогов через `useAudienceDraft` (пока грузится — скелетон и гейт `ready`, иначе можно сохранить пустую аудиторию «никому»); dry-run — publisher+ (не только admin).
- **«Скрыто ото всех» — `audiences.is_none` (0051):** третье явное состояние аудитории (кнопка в `AudiencePicker`, ОС 01.09 — запущенную аттестацию прятали, исключая 261 сотрудника по одному). Оверлей: строки правил СОХРАНЯЮТСЯ (снятие флага возвращает прежнюю аудиторию без перенастройки), а пересчёт вычищает `audience_members` в ноль — поэтому все потребители видимости (visible_filter, обходные «audience_id IS NULL ⇒ всем» в аттестациях/квизах, поиск, RAG) гаснут без правок. Семантику «без правил = все» не переопределяли (zero-rule аудитории в проде перевернулись бы молча). Флаг обязан доезжать до КАЖДОГО вызова `audience_matches` (их три, все в resolver'е) — иначе nightly rebuild пере-добавит членов; ветка `is_none` в `set_object_audience` идёт ДО ветки «всем-удалить», обычное сохранение флаг сбрасывает. Идущая попытка при скрытии доживает во вкладке (гейт только на POST attempts), резюм после перезагрузки — 404. Карточка кампании несёт `audience_hidden` → бейдж «Скрыта» (иначе «прошли 0 из 0» читается поломкой). `useAudienceRules` держит `gcTime: 0` — кэш закрытого диалога при повторном открытии сеял бы доредакционные правила, и «Сохранить» молча снимал бы скрытие. Тесты: `test_is_none_beats_everything` (unit), `test_hidden_audience_lifecycle`/`test_hidden_beats_the_delete_branch` (integration). **Состояние «is_all=false без правил» больше НЕ сохраняется** (ОС 01.09): оно заводило аудиторию, означающую «все» (нет include-строк → база все активные), под видом закрытой — сервер отвечает 422 (`set_object_audience`), кнопку «Сохранить» семи диалогов гейтит зеркальная чистая функция `lib/audienceHints.ts::audienceDraftProblem` (unconfigured | empty-include), она же гасит dry-run и рисует красную подсказку в сводке пикера; exclude-only и «скрыто без правил» — легальны. Пять прод-черновиков-аттестаций с таким состоянием остались как есть — их диалоги требуют явного выбора при первом же открытии; data-миграцию не делали (удаление аудитории стирает granted_at членов).

Consumer-доступ = campaign active + окно + audience-членство; admin — всегда. Импорт вопросов из тестов уроков (позиции продолжаются); activate требует ≥1 вопрос → quiz published + батч kind assessment.assigned с дедлайном; отчёт not_started|in_progress|pending_review|passed|failed со срезом org_scope. Активные несданные кампании показываются на витрине (learn_home). **Разбор ответов в отчёте (02.09, только hub-admin):** строка отчёта несёт `attempt_id` ЛУЧШЕЙ завершённой попытки (её балл и показан), клик открывает `GET /learn/assessments/{id}/attempts/{attempt_id}` — вопросы/варианты из СНАПШОТА попытки (шаффл per attempt, текущие QuizQuestion после правки/реимпорта ни при чём), ответы человека, вердикты с ревью-override (`quizzes.py::attempt_results`) и `correct_answers` В ОБХОД `show_correct_answers` (флаг защищает пересдачи от сотрудника, а не прячет ответы от админа-автора; publisher'ам ручка закрыта — их доступ без правильных ответов остаётся ревью-ручкой `GET /learn/quiz-attempts/{id}`). Отчёт админу дополнительно несёт `question_stats` («Сложные вопросы»): по ВСЕМ завершённым попыткам квиза, бакет по PROMPT (реимпорт = REPLACE с новыми id — бакет по id расщеплял бы вопрос; тот же приём, что «Темы провалов»), open без ревью не судятся, «не ответил» считается ошибкой. Рендер текста ответов — чистый `lib/attemptAnswers.ts` (формы значений — по `quiz_scoring._is_correct`).
- **Избранное (ОС 25.08):** ДВЕ ручки на одни строки, и это не дублирование. `GET /learn/favorites/ids` — плоские ключи `тип:id`, без лимита и без join'а: по ним горят звёзды в библиотеке, курсах и ассортименте. `GET /learn/favorites` — экран `/learn/favorites`: 50 последних записей, названия и ссылки из `search_documents`, **LEFT JOIN** — снятый с публикации объект остаётся строкой «недоступно сейчас», а не исчезает молча. Считать подсветку по второму списку нельзя: лимит и индекс погасили бы часть звёзд без закономерности. Избранное ключуется `employee_profiles.id`, `toggle` без учебного профиля отвечает 404 — звезду в этом случае прячет клиент (`FavoriteStar`). Типы ровно четыре (`FAVORITE_TYPES`), уроков среди них нет: они не индексируются.
- **Скачивание файла материала — подписанным адресом, ГОТОВЫМ заранее (фикс iOS, 02.09, две итерации):** прежний путь «blob через axios + `window.open('')` + `win.location=`» на iOS standalone-PWA упирался в белый `about:blank`. Причина глубже, чем blob: **оверлей `window.open` в standalone вообще не скриптуется** — присвоение `win.location.href` игнорируется и для https (первая итерация фикса с навигацией окна на подписанный URL не помогла, подтверждено на устройстве). Работает только `window.open(готовый_адрес)` ПРЯМО в жесте клика — как у материалов-ссылок. Поэтому выдача `get_library` кладёт в `MaterialResponse.download_url` подписанный `GET .../materials/{id}/file?v&e&s` (HMAC `issue_token` с часовой сеткой — URL побайтово стабилен между рефетчами; ключ `material-file:{id}:{version_no}` — новая версия аннулирует старые ссылки; отдача без Bearer, сессия bypass как `/api/media`, **обязательно `content_disposition_type="inline"`** — attachment iOS-оверлей ни отрисовать, ни скачать не умеет, белый экран (итерация 3); XSS-класса нет: `LIBRARY_MIME` без html/svg + сниффинг). Клик: `void trackOpen()` (ack-гейт, БЕЗ await — задержка выбила бы навигацию из жеста) + `window.open(download_url)`. **Итерация 4 (финальная для standalone):** встроенный просмотрщик PWA office-файлы не рендерит ВООБЩЕ — лог прода зафиксировал 200 + inline и белый экран; поэтому в standalone (`lib/standalone.ts::isStandalone`, вынесен из CertificatePage) клик идёт через `navigator.share({files})`: байты качаются `materialFile` (Bearer работает, открытие трекается), имя — `lib/materialFileName.ts::materialDownloadName` (чинит WEEEK-артефакты `file_name="xlsx"`), AbortError шторки — не ошибка, прочие сбои (истёкшая активация жеста на большом файле) — фолбэк на `window.open(download_url)`. Ручка `GET .../download-link` (auth, track_open, TTL 600с) осталась фолбэком для старых бандлов/кэшей без `download_url`. Inline-просмотр (`materialFile`, pdf/картинки) — blob-путём, он окна не навигирует. Тест — `test_library.py::test_signed_download_link_for_ios`.
- **Материал-ссылка и смена типа «Файл ↔ Ссылка» (02.09):** `kind ∈ (file, link)` живёт с 0017 (ссылка = `url`, версий нет, ack с `version_no=0`, «Открыть ссылку» = `/open` + `window.open`), но тип был неизменяем. Теперь `MaterialUpdate.kind` меняет тип у существующего материала; `update_material` применяет НЕ слепым setattr, а через эффективное состояние: link требует URL (закрыта и API-дыра `PATCH {"url": null}` — публиковалась ссылка без адреса), file обнуляет `url` и восстанавливает `current_version_no = MAX(version_no)` (нумерация загрузок идёт от MAX из БД — цикл file→link→file безопасен), у ОПУБЛИКОВАННОГО link→file без загруженных версий — 422 «Сначала загрузите файл» (гейт `change_status` ловит только переход В published). Ack-семантика — сама собой: эффективная версия N↔0, поэтому re_ack-материалы честно требуют повторного ознакомления, а при `re_ack_on_new_version=false` отметка любой версии остаётся валидной; гейт «сначала откройте» — на МАТЕРИАЛ (view_history), старое открытие файла удовлетворяет его и для ссылки (так же платформа живёт с новыми версиями). Зеркала 422 «published link→file без версий» на клиенте нет сознательно: клиент не знает истории версий, случай редкий, тост показывает серверный текст. Тесты — `test_library.py::test_link_material_lifecycle_and_url_guard` + `test_material_kind_switch_*`.
- **Аудитория раздела библиотеки (ОС 25.08):** `PUT /learn/library/sections/{id}/audience`, publisher, тот же `set_object_audience`, что у материала. Закрытый раздел прячет ВСЕ свои материалы, включая открытые всем (`get_library` отсекает по `visible_section_ids`, `_material_visible_to` — по `section_id`). **Наследования по `parent_id` НЕТ:** закрытый родитель не закрывает вложенный раздел, правило живёт в одном месте и про дерево не знает. Удаление раздела с `?force=1` снимает ограничение с материалов вместе с самим разделом — диалог удаления обязан это называть.
- **Роли:** JWT hub:admin|member|viewer + hub-side `org_role` (employee|tu|franchisee_owner|office → скоуп аналитики через `org_scope.resolve_scope`) + `content_role` (none|author|publisher → права на контент, с Ф1).

## Безопасность

- JWT claims читаются **только** через `signaris-auth-client` — никакого ручного `jwt.decode`.
- CORS на backend разрешает только `https://hub.signaris.ru` и `https://hub-staging.signaris.ru`.
- Rate-limit через Redis (с DB-fallback): паттерн скопирован из `CentralAuthService/app/security/rate_limit.py`.
- Refresh-cookie общий на `.signaris.ru`. Для PWA standalone (iOS) — режим `X-Auth-Mode: api`, refresh-token в IndexedDB.
