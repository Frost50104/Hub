# Перенос задач из WEEEK → Hub (2026-08-25, В ПРОДЕ)

UPPETIT вёл задачи в WEEEK (воркспейс `UPPETIT`, id 732085, 41 участник) и переехал
в Hub. Здесь — что перенесено, что потеряно безвозвратно, как повторить прогон
и чем ограничена идемпотентность.

## Объём (решение владельца)

Проекты, в которых заводили задачи в 2026 году: **47 проектов, 16 703 задачи**
(2 668 открытых, 14 035 выполненных, 2 818 подзадач), вся их история с 2022 года.

Что осталось за бортом ОБЪЁМА:

| | |
|---|---|
| 14 966 задач в 98 удалённых проектах | метаданных проектов API уже не отдаёт — не переносимо в принципе |
| 4 317 личных задач без проекта | принадлежат личным пространствам конкретных людей |
| ~100 проектов без активности в 2026 | решение владельца по объёму |

## Что потеряно безвозвратно

- **Комментарии.** В публичном API WEEEK их нет: проверены `/tm/tasks/{id}/comments`,
  `/tm/task-comments`, `/tm/comments`, `/tm/tasks/comments`, `/tm/task/{id}/comments` —
  все 404. Единственный оставшийся путь — ручной экспорт из UI аналитики WEEEK,
  пока подписка жива.
- **Вложения выполненных задач** — примерно 9 500 файлов. Не влезали в свободное место
  VPS; переносили только у открытых (395 файлов, 0,36 ГБ) плюс картинки из описаний.
- **Повторы задач** (`repeat`, 601 штука) и **учёт времени** (`timeEntries`, 39) —
  в Hub таких сущностей нет.
- **Наблюдатели** (`subscribers`, 37 218 связей) — намеренно: это фабрика уведомлений.
- **История изменений** — в ленте задачи остаётся одно событие «создана»
  с исторической датой.
- **3 картинки из описаний** — их `<img src>` в WEEEK не подписан и отдаёт 403,
  а во вложениях задачи этих файлов нет (остальные 95 спасены именно оттуда).
- **7 файлов вне белого списка** (3 `.rar`, 3 `.cdr`, 1 `.MOV`) — `ALLOWED_MIME`
  ради переноса не расширяли, имена ушли в описание.

## Инструменты

| | где | что делает |
|---|---|---|
| сборщик | `tools/import_weeek/` (локально) | WEEEK API → `weeek-bundle/` |
| проход 1 | `app/jobs/import_weeek_bundle.py` | bundle → БД и файлы |
| проход 2 | `app/jobs/backfill_weeek_assignees.py` | доставить исполнителей позже |
| общее | `app/jobs/weeek_common.py` | детерминированные id, сборка описания |

```bash
# локально: выгрузка (кэш в .weeek-cache/) и сборка
export WEEEK_API_TOKEN=…                       # только в окружении, не в файлах
.venv/bin/python -m tools.import_weeek.fetch --details
.venv/bin/python -m tools.import_weeek.build_bundle --out weeek-bundle
rsync -az weeek-bundle/ …:/opt/signaris-hub/weeek-bundle/

# на VPS: разбор, затем запись
cd /opt/signaris-hub && systemd-run --uid=signaris \
  --property=EnvironmentFile=/opt/signaris-hub/.env \
  --property=WorkingDirectory=/opt/signaris-hub --wait --pipe --collect \
  .venv/bin/python -m app.jobs.import_weeek_bundle \
    --bundle ./weeek-bundle --tenant-slug uppetit --actor-email pp@uppetit.ru [--apply]
```

`set -a; . .env` для этого не годится: bash срезает кавычки у
`SIGNARIS_HUB_CORS_ORIGINS=["…"]`, и pydantic падает на разборе (найдено 24.08).

## Почему импортёр обходит `create_task_record`

Сервис ОБЯЗАН сделать две вещи, неверные для переноса архива:

1. `ensure_watcher(reason="creator")` на каждой задаче (`app/services/tasks.py:124`).
   На 16 703 задачах актёр становится наблюдателем всего: любой чужой комментарий
   и любая отметка «выполнено» шлют ему пуш. «Создать и потом удалить» оставляет
   окно, в которое может попасть падение.
2. `set_done` ставит `datetime.now(UTC)` (`app/services/stages.py:135`), а у 14 035
   задач есть настоящая дата закрытия за 2022–2026.

Плюс цена: 8–10 round-trip'ов на задачу против пачки на 500 строк
(`app/api/tasks_import.py:9` прямо пишет, что путь рассчитан на ≤2000 строк).

Заменители каждой из девяти проверок сервиса перечислены в докстринге джобы;
каждая закрыта тестом в `tests/integration/test_import_weeek.py`. **Любая правка
импортёра обязана оставить зелёными: ноль `task_watchers.added_reason='creator'`,
ноль `notifications`, `done ⟺ completed_at`, подзадача ровно одного уровня,
этап своего проекта, `next_task_seq > max(seq)`.**

## Идемпотентность и чего она НЕ покрывает

Строки Hub адресуются детерминированным `uuid5` от `(тенант, вид, id в WEEEK)` —
`weeek_common.hub_id`. Отсюда:

- повторный прогон видит строку по первичному ключу и пропускает её;
- падение на середине лечится перезапуском, файла состояния нет;
- проход 2 находит задачу по её номеру в WEEEK, карта-файл не нужна.

**Не покрывает:** переименования. Новое имя доски или изменившийся ключ проекта
не подтянутся — джоба существующие строки не переписывает. Это осознанно:
перезапуск не должен затирать ручные правки. Переименование — руками в UI.

**Ключ вложения — ПАРА (задача, файл)**: один и тот же файл WEEEK бывает приложен
к двум задачам, и общий id ронял `task_attachments_pkey` (поймано на staging 25.08).

## Что поймала репетиция на staging (25.08)

Три дефекта, которые тесты на синтетическом бандле не ловили — их видно только
на живых данных:

1. **Один файл на двух задачах** ронял `task_attachments_pkey` — весь проект
   уходил в ошибку. Ключ вложения стал парой «задача + файл».
2. **Три файла соврали расширением** («IMG_7866.HEIC» внутри JPEG, «.png» —
   WebP, «.jpg» — PNG): Hub отвергал их по `sniff_mismatch`. MIME определяется
   по магическим байтам, расширение — только фолбэк для zip/OLE/текста.
3. **`GET /projects/{id}/custom-fields` отдавал 500 на весь проект.**
   `CustomFieldOption.id` — `max_length=32` (`app/schemas/custom_field.py:24`),
   а WEEEK отдаёт 36-символьный UUID. В JSONB ограничения нет, поэтому запись
   прошла молча, а схема ответа развалилась при чтении — кастом-полей в карточке
   просто не было. Теперь id опции схлопывается в `UUID(x).hex` (ровно 32,
   детерминированно), а `_validate` в джобе отказывается импортировать манифест
   с длинным id.

**Урок на будущее:** каждый потолок `max_length` в схемах ответа, у которого в
БД нет парного ограничения, — это мина для любого импорта. Проверять их
надо в валидации бандла, до первой вставки.

## Известные компромиссы

- **`GET /projects/{id}/tasks` не пагинируется** (`app/api/tasks.py:145`). Замер на
  staging после импорта: «Подбор линейного персонала» — 2 551 задача за **407 мс**
  на сервере, остальные крупные проекты 175–240 мс, сайдбар 59 мс, поиск ~50 мс,
  дашборд 65 мс. Прод крутится на одном воркере, так что 0,4 с — это пауза для всех.
  Архивировать выполненные ради облегчения списка НЕЛЬЗЯ: поиск исключает архивные
  (`app/api/search.py:240`), и архив стал бы ненаходимым. Фикс, если станет больно, —
  `limit`/курсор и «показать ещё» отдельным релизом.
- **Широкие доски.** «Локальный маркетинг» — 61 этап, «Дизайн» — 46, «Бухгалтерия
  Аппетит» — 23, «Ввод/вывод сотрудников» — 20, «Поиск персонала офис» — 18.
  Это их реальная структура (колонки как точки продаж и помесячный архив), в WEEEK
  прокручивали ровно то же. Если решат схлопнуть — колонки этих пяти придётся
  разносить по проектам: секций больше нет (0047/0048, они стали метками), и
  второй оси группировки внутри проекта не осталось. Инструмент для этого уже
  есть — `app/jobs/split_project_by_labels.py` (26.08 им разнесён «Подбор
  линейного персонала»); он берёт метку за ось разделения, поэтому колонку
  сначала пришлось бы превратить в метку.
- **Два вложения тяжелее `attachment_max_bytes`** (20 МБ): «Вводная лекция
  (обновленная).pdf» 55,3 МБ и «Локальный наружка на 50 адресов.pptx» 23,5 МБ.
  Лимит — правило ручки загрузки, скачивание работает; перезалить их через UI
  не получится.
- **6 386 задач (38%) приехали БЕЗ статуса** — в WEEEK у них колонки не было вовсе
  (5 325), либо доску удалили целиком (867), либо снесли колонку (194). Такая
  задача есть в списке, календаре и поиске, но не на доске: `tasks.stage_id IS
  NULL` (миграция 0046, сделана ради этого переноса). Синтетической колонки-
  приёмника нет — свалить их в первый этап значило бы соврать, а отдельная
  колонка «Без колонки» собирала бы 1 380 карточек из 2 551 в одном проекте.
  Из 2 668 открытых задач объёма без статуса **1 673 (62%)**: на досках
  «Доработок отдела развития» остаётся 190 карточек из 1 422.
- **548 подзадач с родителем в другом проекте и 178 сирот** импортированы обычными
  задачами: связь оставила бы их невидимыми (доска фильтрует `!parent_task_id`,
  список подзадач собирается из задач того же проекта). В описании — ссылка на
  родителя.
- **«Инициатор» (кастом-поле) перенесён как `text` с ФИО**, а не `person`: тип
  `person` требует `employee_id`, а он есть у пятерых из 41 — 96% значений пропали бы.
- **Батч кастом-полей проекта — 1,25 МБ на «Бухгалтерии Аппетит».**
  `GET /projects/{id}/custom-field-values` отдаёт все значения всех задач
  (`app/api/custom_fields.py:246` — «bounded by defs.count × tasks.count, both
  manageable for Hub-scale projects»). На 1 636 задачах × 6 полей это ~1,25 МБ
  несжатых, 127 КБ по проводу и ~1 с. Пока терпимо, но растёт произведением.
- **`overdue`: антидубль 23 ч против суточного таймера.** К переносу отношения не
  имеет, но заметно на объёме: `ANTI_DUP_WINDOW = 23h` (`app/jobs/overdue.py:28`)
  короче интервала таймера, поэтому напоминание о просроченной задаче уходит каждый
  день заново. В объёме переноса просроченных открытых задач всего 4.

## Проход 2 — доставка исполнителей

На момент импорта в Hub было пятеро из 41 участника WEEEK. Остальным проход 1
вписал в описание строку «_Исполнитель в WEEEK: Имя_». Проход 2 находит тех, кто
с тех пор зашёл, ставит их исполнителями и снимает строку:

```bash
.venv/bin/python -m app.jobs.backfill_weeek_assignees \
  --bundle ./weeek-bundle --tenant-slug uppetit --actor-email pp@uppetit.ru [--apply]
```

Гонять можно сколько угодно раз. Он **не** трогает задачи, где исполнитель уже
есть (в том числе поставленный руками), и **не** шлёт уведомлений
(`apply_assignee_side_effects(..., notify=False, record=False)` — у обоих полей
по умолчанию `True`, и без явного выключения ушло бы до 740 пушей «Вам назначена
задача» про задачи 2022 года). Описание, переписанное человеком, остаётся как есть.
В отчёте — поимённый список тех, кого всё ещё нет в Hub.

## Откат

`pg_restore` снимка — самый надёжный путь, пока в Hub нет живой работы. Адресный
вариант: собрать `storage_key` вложений, удалить файлы (осиротевшие с диска не
убирает никто — `unlink` есть только в ручке удаления вложения), затем
`DELETE FROM projects WHERE id IN (…)` — каскадом уходят задачи, этапы, секции,
вложения, лента, наблюдатели, кастом-поля — и `DELETE FROM project_folders`.
